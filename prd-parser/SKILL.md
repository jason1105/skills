# prd-parser — PRD 解析与结构化

## 定位

工作流第一道关口。目标只有一个：
把任意格式的需求文档，变成 `docs/requirements-structured.md`。

后续所有 Skill 都以该文件为输入，文件不存在则所有下游 Skill 停止执行。

## 落位与基线（仓有 GitLab 议题/MR 流程时）

- 输入是**基线目录**（`NN-需求号/`：00-来源记录/01-原始资料/02-解析/03-差异与疑点）时，结构化基准落该目录 `04-需求结构化基准.md`（目录最大号递增，不叫 requirements-structured.md）；此时 02-解析/03-差异与疑点已含部分结构，**以冻结原件为准逐类对齐补全**，不从解析件抄转述
- 冻结 docx 用 python zipfile 抽 `word/document.xml` 文本（`<w:p>` 分段、拼 `<w:t>`）；评审回复的 Q&A 逐条读，Q 编号作来源锚（回复有重号/跳号时照录进疑点清单，不重排）
- 冲突口径已被回复裁定的（两份需求正文对同一场景写法不一致、回复选边），BR 写裁定侧、疑点表登记原文冲突与裁定出处；**建议式/非终局的回复**（「建议…」「暂无规则，出现再定」）不算裁定——进疑点清单带临时假设
- 产出后走 prd-source-baseline 三查再进 prd-detail-design；Step 1-3 的对话内输出惯例在基线目录模式下可合并为「成文即落盘＋自检报告」

## 前置检查

运行本 Skill 前检查：

```
docs/ 目录是否存在？
→ 不存在：创建 docs/ 目录，继续执行。
→ 已存在且有 requirements-structured.md：
    提示"文件已存在，是否覆盖还是追加新需求？"，等用户确认后继续。
```

## 执行步骤

### Step 1：通读全文，不要边读边输出

完整阅读 PRD 后，在脑中标记三类内容：
- **确定规则**：有明确判断标准、可写成测试断言的描述
- **意图描述**：含"希望""可以""最好"等软性措辞，需要澄清
- **矛盾/缺失**：前后不一致、关键信息缺失的段落

### Step 2：提取五类结构化内容并输出

按以下固定格式输出到对话中，**不立即写文件**，用户确认结构正确后再执行 Step 4：

````markdown
## 1. 功能清单

| 编号 | 功能名称 | 一句话描述 | 优先级 | 来源 |
|------|----------|-----------|--------|------|
| F01  | AGC报价提交 | 资源向市场提交调频报价单 | P0 | 第3节 |

> 优先级：P0=核心（缺失系统无法运行）/ P1=重要（影响主流程）/ P2=增强（后续迭代）

## 2. 业务规则列表

每条规则必须满足：**可测试、有明确判断标准、表述完整**。

| 编号 | 业务规则（可直接写成测试断言） | 所属功能 | 来源 |
|------|-------------------------------|----------|------|
| BR01 | 报价功率 ≤ 资源申报容量 × 105% | F01 | 第4节 |
| BR02 | 报价提交时间必须在截止时间之前 | F01 | 第4节 |

## 3. 模糊/矛盾点清单

| 编号 | 问题描述 | 涉及功能 | 建议澄清方式 | 临时假设 |
|------|----------|----------|--------------|----------|
| Q01  | 截止时间的时区未说明 | F01 | 询问产品经理 | 暂按 UTC+8 |

## 4. 边界条件与异常流

| 编号 | 触发场景 | 期望系统行为 | 来源标注 |
|------|----------|--------------|----------|
| E01  | 超过截止时间提交 | 拒绝，返回 BID_DEADLINE_EXCEEDED | 文档明确 |
| E02  | resourceId 为空 | 拒绝，返回 INVALID_ARGUMENT | 推断 |

> 来源标注：文档明确 / 推断（需确认）/ 行业惯例

## 5. 核心实体识别

| 实体名（英文） | 中文名 | 一句话说明 | 与其他实体关系 |
|----------------|--------|-----------|----------------|
| Resource | 资源 | 参与辅助服务的发电/储能资源 | 拥有多个 Bid |
| Bid | 报价单 | 市场报价的基本单元 | 属于 Resource |
````

### Step 3：生成待确认事项清单

紧接在五类内容之后输出，按优先级分级：

```markdown
## 待确认事项（开始技术方案设计前必须解决高优先级项）

### 高优先级（影响数据模型设计）
- [ ] Q01：截止时间时区问题 → 联系产品确认

### 中优先级（影响业务逻辑实现）
- [ ] （如有）

### 低优先级（可先基于临时假设开发）
- [ ] （如有）
```

### Step 4：用户确认后写入文件

用户确认结构无误后（或明确说"直接写文件"），写入 `docs/requirements-structured.md`：

```markdown
---
source_doc: [原始文档名或描述]
parsed_at: [YYYY-MM-DD]
parsed_by: Codex (prd-parser v1.0.0)
status: PENDING_CLARIFICATION   # 有未解决的高优先级澄清项时
# status: READY_FOR_DEVELOPMENT # 所有高优先级项已解决时
clarification_count: [Q编号数量]
---

[以上五类结构化内容完整写入]
```

### Step 5：输出衔接提示

```
docs/requirements-structured.md 已生成。
状态：[PENDING_CLARIFICATION / READY_FOR_DEVELOPMENT]

发现 [N] 个待确认项，其中高优先级 [M] 个（影响数据模型）：
[列出高优先级 Q 编号和一句话描述]

→ 下一步：解决高优先级澄清项后，运行 task-planner
  （若选择基于临时假设继续，task-planner 会提示确认）
```

## 自检清单（Step 4 执行前必过）

- [ ] 「建议澄清方式」列禁止跨文件编号缩写（「随⑨评审逐项过(07号§9)」「同上」类）——读者无法解码；直指本目录文件「登记于 03-差异与疑点 疑点 N」，溯源尾注可留

- [ ] 每条 BR 都可以独立写成单元测试的 `assert` 语句
- [ ] 模糊点都有"建议澄清方式"，不能只写"待确认"
- [ ] E（边界条件）覆盖了：空值、超限值、并发重复、超时、权限不足
- [ ] 来源标注为"推断"的条目已单独列出
- [ ] 核心实体之间的关系已全部描述
