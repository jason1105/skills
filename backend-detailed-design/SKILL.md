# 详细设计

## 目标

基于需求分解阶段的任务列表和需求补充记录，产出完整的技术设计文档，包括模块划分、核心流程、数据模型概要、技术选型等，为后续的 DDL 设计、API 设计和编码实现提供依据。

## 产出物充分性要求

本阶段的产出物同时服务于 DDL 设计、API 设计和编码实现三个下游阶段。**其他后端工程师必须能够根据设计文档实现后端所有功能。** 具体来说：

- 清楚每个模块的职责边界，知道代码应该放在哪里
- 理解每个核心流程的完整步骤，包括正常流程和异常分支
- 根据数据模型概要直接开始设计表结构
- 根据技术决策记录理解"为什么选这个方案"而非其他方案
- 按照异常处理策略和错误码规范编写代码，无需再讨论

**只要不是 100% 明白的，必须向用户确认。**

## 分层架构

分层模型的具体命名由项目技术栈和团队约定决定，常见模型如下，选用一种即可：

| 分层模型 | 典型语言/框架 | 层级 |
|---------|--------------|------|
| 经典三层 | Spring Boot、Django | Controller / Service / Repository |
| Clean Architecture | 通用 | Handler → UseCase → Repository → Infrastructure |
| 六边形架构 | 通用 | Adapter → Application → Domain → Port |
| MVC + Manager | 部分 Java 项目 | Controller → Service → Manager → DAO |

**关键原则（任何分层模型都适用）**：
- **入口层**：负责协议解析（HTTP 请求→对象）、参数校验、权限判断、组装响应，不含业务逻辑
- **业务层**：核心业务逻辑、事务控制、跨模块编排；可再分为 Application（流程编排）和 Domain（业务规则）
- **数据层**：仅负责数据存取，不含业务判断
- **依赖方向**：入口层 → 业务层 → 数据层，禁止反向依赖和跨层调用

在详细设计文档中需明确：
- 采用哪种分层模型
- 每层的类/模块清单及其职责
- 跨层调用规则（如是否允许 Controller 直接调用 Repository）

### 示例（以经典三层为例）

#### Controller / Handler 层
| 类名 | 所属模块 | 职责 |
|------|----------|------|
| XxxController | 模块A | 接收请求、参数校验、调用 Service、组装响应 |

#### Service / UseCase 层
| 接口/类名 | 所属模块 | 核心方法 | 职责说明 |
|-----------|----------|----------|----------|
| XxxService | 模块A | method1(), method2() | [每个方法做什么] |

#### Repository / DAO 层
| 类名 | 所属模块 | 职责 |
|------|----------|------|
| XxxMapper | 模块A | [负责哪些表的数据访问] |

- 设计要考虑目标数据库的特性和限制（具体数据库在 backend-dev 启动时已确认）
- 异常处理和错误码规范在此阶段确定，后续阶段遵循
- 流程设计中的"异常分支"不能只写"返回错误"，要写清楚具体错误码和错误信息
- 数据模型概要不是只列实体名，必须包含核心字段及其用途
- **只要不是 100% 明白的，必须向用户确认**
