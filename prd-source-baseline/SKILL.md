# 详设源件基线与落位（生成详设前的三查）

## When to Use

- 用户要求「根据 XX需求.md 生成需求详细设计」且仓有 GitLab 议题/MR 流程时，动笔前先跑本 skill 的三查
- 本 skill 是 `prd-detail-design` 生成流程的前置步骤：基线钉不准，详设评审对象会随 rebase 漂移

## 一查：基线版本（在途 MR 不吸收）

1. 把基线钉在**已合并默认分支**的源件版本上：`git show origin/<default>:<源件路径>` 读定版本号，与工作树版本 diff 确认无未合并差异混入
2. 查在途 MR：`glab api "projects/<id>/merge_requests?state=opened"` → 逐条 `.../merge_requests/<iid>/changes` 看是否改同一源件（该 13.11 无 `/diffs` 端点、404；用 `/changes`；权威量级以 `git fetch origin <branch>` 后 `git diff --stat origin/<default>...origin/<branch> -- <源件>` 为准）
3. 命中在途 MR 时四件事：① 详设不写它的未合并口径（新 REQ、改写条目、新裁决）；② 详设文头基线行写明「源件 vX.Y」；③ 附录「不纳入/后续」登记「该 MR 合并后详设须按新版迭代一轮」；④ 本任务 MR 描述写明两 MR 改同一文件、合并/rebase 顺序待用户拍板

原因：详设会被文对文评审——评审对象必须在评审期间稳定；未合并口径随 rebase 漂移会让评审记录失效，吸收未合并裁决还会把「提议」当「拍板」写进冻结件。

## 二查：源件位置（性质与目录匹配）

需求类文档放需求目录，不放设计目录；输入件位置不对时先归位再生成，两步进同一议题/MR、各自独立提交（一笔移位、一笔新增详设）。归位固定流程：

1. `git mv` 保历史（移位＋少量行改并存时 rename 相似度高，历史可追）
2. 文头「文档」行改新路径，括号保留历史路径链（逐次迁移来源）
3. 文内相对链接按新目录深度重算（变深加路径段，变浅删段）
4. 修订记录追加一行「（迁移/归位，版本号不变）」，技术内容不动
5. 引用方活链接同步修：`grep -rn "<文件名>" docs --include="*.md"`（排除归档目录），只改 markdown 链接目标与「同目录」类指向措辞；历史修订记录里的旧路径文字保留原文
6. 收尾 `grep -rn "<旧路径>"`：全仓命中应只剩历史/归档记录

## 三查：输出落位（编号占号）

1. 输出文件编号按目标目录现行最大号递增；**先查在途 MR 新增文件**（changes 中新增状态的路径）是否占用相邻编号——不看在途 MR 会撞号，两 MR 合并后同目录乱序
2. 文件名前缀与后续卡片/原型保持一致（详设是姊妹 skill 的输入，同前缀同目录）
3. 详设自检脚本骨架：REQ/NFR/场景覆盖、相对链接零死链、重复标题、表格列数一致；数字口径抽查（源件中的量词数字能在详设命中）

## 铁律

- 详设只写已合并口径；在途 MR 的新增 REQ 与改写条目不进正文
- 基线版本号写进详设文头，不写「最新版」这类会漂移的表述
- 与在途 MR 的合并/rebase 顺序是用户拍板项，agent 只列明关系不代答
