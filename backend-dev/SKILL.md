# 后端研发全流程

## 目标

将一个业务需求从理解到交付，经过需求分解、详细设计、DDL 设计、API 接口设计、编码实现、验证、沉淀七个阶段，产出可交付的后端代码及配套文档。

## 核心原则

### 产出物充分性原则（所有子 skill 必须遵循）

**每个阶段的产出物必须信息充分，足够让一个不了解上下文的工程师仅凭该文档独立完成后续工作。**

具体要求：

- **自包含**：产出物不依赖口头沟通或隐含知识，所有决策、约束、上下文都写在文档中
- **可执行**：工程师读完文档后能直接动手，无需再问"为什么"或"具体怎么做"
- **无歧义**：避免"适当处理"、"参考常规做法"等模糊表述，给出明确的方案和参数
- **完整链路**：每个流程从入口到出口、从正常到异常都有覆盖，不留空白

**自检问题**：把文档交给一个刚入职的工程师，他能否仅凭文档完成工作？如果不能，文档就不够充分。

### 跨 Skill 引用与协作原则（所有子 skill 必须遵循）

**执行任何 skill 完成具体任务时，允许引用其他已存在的 skill 来补充能力或完成专项工作；当用户对 skill 使用有明确偏好时，优先满足用户偏好。**

具体规则：

1. **允许引用**：执行子 skill 时，可以引用、调用或参考其他已存在的 skill（包括本包内的兄弟 skill、用户全局 skill `~/.claude/skills/`、项目级 skill `.claude/skills/`）。例如实现阶段引用 `code-scan-report` 做安全扫描、引用 `update-skill` 沉淀经验等。
2. **先核实再引用**：引用前先确认目标 skill 存在且语义匹配，禁止凭空假设 skill 名或能力。不存在时直接告知用户而非编造。
3. **用户偏好优先**：当用户明确表达对 skill 使用的偏好（如"用 X skill 处理"、"不要用 Y"、"这步换成 Z"），用户偏好优先级最高，直接采纳。
4. **强制前置不可被偏好覆盖**：以下属于本 skill 的强制约束，不被用户偏好绕过，必须执行（除非用户在确认时明示豁免）：
   - `backend-implementation` 的 `references/coding-standards.md` 必读检查
   - `references/security/` 安全合规参考的按需加载
   - 每阶段后的 `backend-quality-gate` 自动质量门禁
5. **透明告知**：引用其他 skill 时简短告知用户："已引用 X skill 处理 Y"，并允许用户中途调整。

## 技术栈

技术栈不做限定，在首次启动时向用户确认以下信息并记录：

| 确认项 | 示例 |
|--------|------|
| 语言 | Java / Go / Python / ... |
| 框架 | Spring Boot / Gin / FastAPI / ... |
| 数据库 | MySQL / PostgreSQL / 达梦8 / ... |
| 构建工具 | Maven / Gradle / go mod / ... |

确认结果记入需求分解文档或详细设计文档中，后续阶段遵循。

| 文档 | 加载阶段 |

| `README.md`（索引） | 每个阶段先读索引确定需要加载的文档 |
| `secure-coding.md` | 实现阶段 |
| `security-features.md` | 详细设计、DDL 设计 |

    │   └── 05-验证报告.md

**需求文件夹命名**：`docs/` 下的需求目录必须以零补位数字前缀编号，按时间顺序排列，格式：`NN-需求名`（如 `01-用户权限管理`、`02-订单导出功能`）。新建需求时取当前 `docs/` 下最大编号 +1。需求名须经用户确认。

**知识沉淀目录**：`docs/知识沉淀/` 用于存放研发过程中学到的技术知识（框架用法、依赖关系、设计约束等）。文件以**分类名称作为前缀**，格式 `{分类}-{主题}.md`（如 `maven-local-cache.md`、`spring-setdata-overload.md`）；当文件数超过 15 个时，过渡为子目录结构 `docs/知识沉淀/{分类}/{主题}.md`。

## 子任务编排

按以下顺序执行，每个阶段完成后须经用户确认方可进入下一阶段。

```
阶段 0  需求分解         backend-requirement-breakdown
   ↓
阶段 1  详细设计         backend-detailed-design
   ↓
   ├─→ 阶段 2a  DDL 设计       backend-ddl-design        ┐
   │                                                       ├─ 可并行
   └─→ 阶段 2b  API 接口设计   backend-api-design         ┘
   ↓
阶段 3  实现             backend-implementation
   ↓
阶段 4  验证             backend-verification
   ↓
阶段 5  沉淀             backend-artifact-summary
```

**质量门禁**：`backend-quality-gate` 在以下时机**自动触发**——每个子阶段完成后、用户确认前，自动调用 `backend-quality-gate` 对该阶段产出物做单阶段检查。检查报告无阻断项时才提交用户确认；有阻断项则修复后重新检查，直到通过。用户也可随时主动要求对任意阶段或全量做质量门禁检查。

**并行说明**：DDL 设计（阶段 2a）与 API 接口设计（阶段 2b）均依赖详细设计的输出，彼此无依赖，可并行执行。

## 执行步骤

### Step 0: Help 检查

如果用户说"help"或"帮助"，直接显示上面的「使用说明」内容，不继续执行后续流程。

1. **启动**：收到用户的业务需求后，先确认需求范围和需求名称。
2. **创建需求文件夹**：在 `docs/` 下创建以需求名命名的文件夹，如 `docs/用户权限管理/`。需求名须经用户确认。
3. **初始化进度文件**：在 `docs/{需求名}/PROGRESS.md` 中创建进度跟踪表。
4. **依次调度子 skill**（每个子 skill 接收 `{需求名}` 作为上下文参数）：
   - 调用 `backend-requirement-breakdown` → 自动调用 `backend-quality-gate`（单阶段检查）→ 修复阻断项（如有）→ 更新 PROGRESS.md → 等待用户确认。
   - 调用 `backend-detailed-design` → 自动调用 `backend-quality-gate`（单阶段检查）→ 修复阻断项（如有）→ 更新 PROGRESS.md → 等待用户确认。
   - 调用 `backend-ddl-design` 和 `backend-api-design`（可并行）→ 两个阶段都完成后，分别自动调用 `backend-quality-gate`（单阶段检查）→ 修复阻断项（如有）→ 更新 PROGRESS.md → 等待用户确认。
   - 调用 `backend-implementation` → 自动调用 `backend-quality-gate`（单阶段检查）→ 修复阻断项（如有）→ 更新 PROGRESS.md → 等待用户确认。
   - 调用 `backend-verification` → 自动调用 `backend-quality-gate`（单阶段检查）→ 修复阻断项（如有）→ 更新 PROGRESS.md → 等待用户确认。
   - 调用 `backend-artifact-summary` → 自动调用 `backend-quality-gate`（**全量检查**）→ 修复阻断项（如有）→ 更新 PROGRESS.md → 等待用户确认。
5. **交付**：所有阶段完成后，告知用户交付物总览位置。

## Git 提交规范

所有阶段产生的代码改动均遵循以下规范。

### 提交信息格式

```
<type>: <简要描述>
```

| type | 用途 |
|------|------|
| `feat` | 新功能 |
| `fix` | Bug 修复 |
| `refactor` | 重构（不改变行为）|
| `docs` | 仅文档变更 |
| `test` | 测试相关 |
| `chore` | 构建、依赖、配置等杂项 |
| `perf` | 性能优化 |

### 提交原则

- **原子提交**：一次提交一个逻辑变更，禁止"大杂烩提交"（同时混入多个不相关改动）
- **提交前自检**：本地编译通过 → 单元测试通过 → lint / 格式化通过，再提交
- **不提交生成物**：编译产物、IDE 配置、本地 `.env` 文件不进代码仓库

### 分支策略

- 实现阶段在 `proj/dev` 分支上创建 `feat/{需求名}` 特性分支
- 验证通过后向 `proj/dev` 提 MR / PR，经代码审查后合入

## 注意事项

- 每个阶段产出物必须经用户确认后才写入文件
- **在所有阶段中，只要不是 100% 明白的，必须向用户确认，绝不假设**
- 用户可随时要求跳过某个阶段（标记为 ⏭️）
- 用户可要求回退到之前的阶段重新执行
- DDL 设计和 API 接口设计可并行，但均须在详细设计完成后开始
- 实现阶段基于 `proj/dev` 分支创建 `feat/{需求名}` 特性分支

## 工程卫生规范

### 反编译文件清理

实现阶段如发现项目根目录或非 `src/` 目录下存在 `.java` 文件（通常是工程师从 JAR 提取的参考副本，如 `com/xxx/.../*.java`），必须提醒用户确认并删除。这类文件不参与编译，但会增加工程师理解代码库的认知成本。

### 知识沉淀机制

每次实现完成后，将研发过程中非显而易见的技术发现整理为独立 Markdown 文档保存到 `docs/知识沉淀/`，避免下次实现时重复探索。**应当沉淀的内容**：

- 查阅 JAR 包（`jar tf`、`javap`）时发现的框架类结构、版本差异
- 解决依赖问题、类型不兼容、版本升级时的根因与解决方案
- 模块架构约束（如某模块不能引入特定依赖的原因）
- 第三方框架非显而易见的用法规则（如方法重载规则、切换行为）

**文档格式**：包含使用场景、Maven 坐标（如适用）、代码示例、常见错误与正确写法。
