# 产出物质量门禁

## 核心原则

**严谨压倒一切**。每一句话都要有详实的依据，不允许哪怕 1% 的猜测。检查结果必须禁得起反复审核。

- 每个检查结论都必须有对应的文件路径、行号或具体内容作为依据
- 不能凭印象或假设下结论
- 发现不一致时，先确认原因再定级

## 目标

对后端研发各阶段的产出物进行合规性检查，确保每个阶段的文档满足对应 skill 的验收标准、跨 skill 约定和安全合规要求。发现问题并给出具体修复建议。

## 与其他 skill 的关系

| Skill | 侧重点 | 互补关系 |
|-------|--------|---------|
| **backend-verification (阶段 4)** | 代码功能是否正确(测试用例, 接口测试, 性能测试) | 验证代码行为 |
| **backend-quality-gate (本 skill)** | 文档是否合规(格式, 完整性, 一致性, 充分性) | 验证文档质量 |

两者互补, 不重叠. 建议在每个阶段完成后运行本 skill, 在实现阶段完成后运行 backend-verification.

## 前置条件

- 至少有一个阶段的产出物已生成且经用户确认
- `docs/{需求名}/PROGRESS.md` 已存在

## 使用方式

**单阶段检查**(推荐在每个阶段完成后立即执行):

```
"检查一下需求分解的产出物"
"需求分解的文档合格吗"
"对详细设计做质量门禁"
```

**全量检查**(所有阶段完成后执行):

```
"检查所有产出物"
"做一次全量质量门禁"
"产出物自检"
```

## 执行步骤

### Step 1: 确定检查范围

读取 `docs/{需求名}/PROGRESS.md`, 确定哪些阶段已完成, 仅检查已完成阶段的产出物.

如果用户指定了某个阶段, 则只检查该阶段.

### Step 2: 逐阶段检查

对每个待检查的阶段, 按以下五个维度执行检查:

**关键检查顺序**: 先检查实际代码/文件实现, 再对照设计文档。**禁止仅看文档就推断代码未实现**。

#### 维度 0: 代码实现优先验证（新增，必须最先执行）

在进行其他维度检查前，先检查实际代码/文件：

| 检查项 | 检查方法 | 要求 |
|--------|---------|------|
| 代码文件存在性 | 使用 Glob 查找相关文件 | 确认文件是否真实存在 |
| 关键内容验证 | 使用 Read 实际读取文件 | 每个结论都必须有文件内容依据 |
| DO 实体类 | 逐一检查每个实体类的字段 | 不能仅凭 DDL 文档推断代码状态 |
| Service/DTO/Controller | 检查对应的实现类 | 确认是否有相关实现 |
| **SonarQube代码质量** | **检查SonarQube扫描报告或实际代码** | **验证Javadoc注释、枚举注释、DTO默认值、魔法值等问题** |

**重要**:

- ✅ 先 Read 代码，再对照文档
- ❌ 禁止顺序颠倒
- ❌ 禁止"文档里写了 ALTER TABLE → 代码肯定没实现"的逻辑
- 区分"文档未更新"和"代码未实现"是两种不同情况
- ⚠️ **SonarQube问题分类及修复方案**：详见 `backend-dev/references/sonarqube-fix-guide.md`

#### 维度 1: 完整性检查

对照该阶段 skill 的**验收标准**(即 SKILL.md 中的"验收标准"章节), 逐条核实:

| 阶段 | 验收标准来源 |
|------|------------|
| 阶段 0 需求分解 | `backend-requirement-breakdown/SKILL.md` 的验收标准 |
| 阶段 1 详细设计 | `backend-detailed-design/SKILL.md` 的验收标准 |
| 阶段 2a DDL 设计 | `backend-ddl-design/SKILL.md` 的验收标准 |
| 阶段 2b API 设计 | `backend-api-design/SKILL.md` 的验收标准 |
| 阶段 3 实现 | `backend-implementation/SKILL.md` 的验收标准 |
| 阶段 4 验证 | `backend-verification/SKILL.md` 的验收标准 |
| 阶段 5 沉淀 | `backend-artifact-summary/SKILL.md` 的验收标准 |

**检查方法**: 阅读产出物文档, 对照验收标准的每一条 checkbox 判定是否满足. 不能凭印象判断, 必须在文档中找到对应内容.

#### 维度 2: 格式规范检查

对照跨 skill 约定(定义在 `backend-dev/SKILL.md` 中)检查:

| 检查项 | 规则 | 怎么查 |
|--------|------|--------|
| 目录命名 | `NN-中划线名称`(如 `00-需求分解`) | 检查 `docs/{需求名}/` 下的目录名 |
| 文件命名 | `NN-中划线名称.md`(如 `00-需求分解.md`) | 检查目录下的文件名 |
| 编号连续 | 从 `00` 开始, 无跳号 | 检查编号序列 |
| 文件格式 | Markdown 格式 | 检查文件扩展名 |
| PROGRESS.md | 已更新到当前阶段 | 检查进度标记 |

#### 维度 3: 一致性检查

检查上下游产出物之间的引用关系是否正确:

| 上游 | 下游 | 一致性检查点 |
|------|------|------------|
| 需求分解 | 详细设计 | 需求分解中的每个功能点在详细设计中都有对应的模块或流程覆盖 |
| 详细设计 | DDL 设计 | 详细设计中的数据模型概要中的每个实体在 DDL 中都有对应的表 |
| 详细设计 | API 设计 | 详细设计中的每个模块在 API 设计中都有对应的接口覆盖 |
| DDL 设计 | 实现记录 | DDL 中的每张表在代码结构中都有对应的实体/模型类 |
| API 设计 | 实现记录 | API 设计中的每个接口在代码结构中都有对应的控制器方法 |
| API 设计 | 验证报告 | API 设计中定义的每个错误码在验证报告中都有对应的测试用例 |
| 需求分解 | 交付物总览 | 需求分解中的所有功能点在交付物总览中都有体现 |

**检查方法**: 从上游文档提取清单(功能点列表/实体列表/接口列表), 在下游文档中逐一查找对应项. 缺失的标记为"一致性缺失".

#### 维度 4: 充分性检查

对照产出物充分性原则(定义在 `backend-dev/SKILL.md` 中)检查:

| 原则 | 自检问题 | 怎么判断 |
|------|---------|---------|
| 自包含 | 文档中是否有"详见XX"指向不存在的文档? 是否有依赖口头沟通的隐含知识? | 搜索所有"详见""参考""参见"引用, 验证目标存在 |
| 可执行 | 一个新工程师读完文档后能否直接动手? | 检查是否有"适当处理""酌情考虑"等模糊表述 |
| 无歧义 | 是否有多种理解方式的描述? | 检查是否有"等""之类""相关"等模糊词 |
| 完整链路 | 正常流程和异常流程是否都覆盖? | 检查每个流程是否有异常分支说明 |

**模糊表述关键词扫描**(在文档中搜索以下关键词, 每找到一个标记为潜在问题):

```
适当处理, 酌情考虑, 参考常规做法, 根据实际情况, 可选, 等等,
视情况而定, 按需, 如有必要, 合理的, 正常返回, 成功
```

> 注意: 上述关键词不一定都是问题, 需要结合上下文判断. 如果该表述在上下文中有明确限定条件, 则不算问题.

#### 维度 5: 安全合规检查

对照该阶段对应的安全自检清单检查:

| 阶段 | 安全自检清单来源 |
|------|----------------|
| 详细设计 | `security-features.md` 末尾的"设计自检清单" |
| DDL 设计 | 检查敏感字段是否标注了加密/脱敏级别 |
| API 设计 | `penetration-defense.md` 末尾的"API 设计自检清单" |
| 实现 | `secure-coding.md` 末尾的"编码自检清单" |
| 验证 | `compliance-testcases.md` 的验证阶段使用指引 |

需求分解和沉淀阶段不涉及安全自检清单.

### Step 3: 汇总检查结果

将所有检查结果汇总为检查报告, 按严重程度分类:

| 严重程度 | 定义 | 处理要求 |
|---------|------|---------|
| **阻断** | 产出物缺失或存在严重错误, 后续阶段无法基于此继续 | 必须修复后才能进入下一阶段 |
| **警告** | 产出物存在不完善的地方, 但不影响后续阶段的进行 | 建议修复, 但可以先继续 |
| **建议** | 可以改进但不影响质量判断 | 按优先级选择性处理 |

### Step 4: 用户确认

将检查报告呈现给用户, 确认后写入文件.

如果存在"阻断"级别的问题, 建议用户修复后再重新检查.

## 输入输出

- 输入:
  - `docs/{需求名}/` 下已完成阶段的所有产出物
  - `docs/{需求名}/PROGRESS.md`
  - 各阶段 skill 的 SKILL.md(读取验收标准)
  - 安全合规参考文档(按需读取)
- 输出: 质量门禁检查报告
- 产出物位置: `docs/{需求名}/quality-gate-report.md`

## 验收标准

- [ ] 每个检查结论都有详实的依据（文件路径/行号/具体内容）
- [ ] 遵循"先检查代码实现，再对照设计文档"的顺序
- [ ] 区分了"文档未更新"和"代码未实现"两种不同情况
- [ ] 每个已完成阶段都已按 5+1 个维度检查（包含维度 0）
- [ ] 每个维度的每条检查项都有明确的 PASS / BLOCK / WARN / INFO 结论
- [ ] 一致性检查覆盖了所有上下游引用关系
- [ ] 充分性检查扫描了模糊表述关键词
- [ ] 安全合规检查对照了该阶段对应的安全自检清单
- [ ] 所有问题都有具体的修复建议(不是"请修复")
- [ ] 问题按阻断/警告/建议三级分类
- [ ] 总结给出了明确的"是否可以继续推进"判断

## 注意事项

- **严谨压倒一切**：每个结论都必须有文件内容依据，不能凭印象或假设
- 检查时必须实际阅读产出物内容, 不能仅凭文件是否存在来判断
- 一致性检查是核心价值所在 -- 单个文档内部的问题容易发现, 跨文档的断链不易察觉
- 模糊表述不一定都是问题, 需要结合上下文判断, 避免过度报警
- 检查报告本身也要遵循"产出物充分性原则" -- 修复建议必须具体到可执行
- 如果某个阶段是从上一轮迭代继承的(非本次生成), 在检查时标注"继承产出物"
- 该 skill 不修改任何产出物, 只生成检查报告; 修复由用户决定
- **跨 skill 引用**：执行本 skill 时可引用其他已存在的 skill 来补充能力；用户对 skill 使用有明确偏好时优先满足，**但本 skill 作为强制质量门禁本身不可被偏好绕过**（详见 `backend-dev/SKILL.md` 「跨 Skill 引用与协作原则」）

## 已知陷阱

- ❌ 检查顺序颠倒：先看文档，后看代码 → 导致误判
- ❌ 仅凭文档推断：看到 ALTER TABLE 就认为代码未实现 → 未考虑可能是文档补充说明
- ❌ 未逐一验证：未逐个检查实体类文件就下结论 → 导致遗漏
- ⚠️ 区分两种情况："文档未更新" vs "代码未实现"是完全不同的问题等级
