# PRD 需求卡片双向溯源原型规范

## When to Use

- 用户要求生成可交互原型／需求卡片／评审材料时
- 已有三件套（详细设计 MD＋需求卡片 MD＋HTML 原型）需要迭代时
- 任意系统均适用，不限 Market；触发词：原型／需求卡片／评审材料
- 与姊妹 skill 分工：`prd-detail-design` 负责《产品需求详细设计》的生成与迭代，本 skill 消费其产出（或用户直接给详设）出卡片＋原型；用户说「从需求出三件套」时先跑 prd-detail-design 再接本 skill

产出「一份详细设计 MD + 一份需求卡片 MD + 一个自包含 HTML 可交互原型」三件套，适用于任意系统（不限 Market）。需求、原型、验收三者编号贯通，双向可跳。

## 三件套产出约定

同一基线日期与需求编号体系（REQ-{需求号}-xxx，见「需求编号与功能标注」节），三个文件同名前缀、同目录：

1. `{系统}_产品需求详细设计.md` — 由姊妹 skill `prd-detail-design` 生成（用户直接给详设时沿用其编号与章节）；本 skill 不重复生成
2. `{系统}_需求卡片.md` — 每条需求一张卡片：适用角色／模块来源／优先级分类／架构承接（有架构文档时）／原型位置链接；正文【1.业务背景】【2.用户故事】【3.功能描述】（编号小节）【4.验收标准】等固定小节。卡片内容从详设七段式抽取：背景←功能业务说明、故事←用户故事句、规则←交互与业务规则、AC←验收标准表
3. `{系统}_可交互原型.html` — 见下

**全仓唯一持续迭代原型的例外**：用户明确指定原型「全仓唯一、持续迭代」时，原型升格为跨阶段共享件——放需求目录的 `00-原型/` 下、文件名带**两位补零序号前缀**（`01-{系统}_可交互原型.html`，与仓内目录编号规则 `01-清单与规格` 一致；不带阶段/需求号前缀），后续阶段在同一文件上追加 REQ 族与视图，不另开文件；卡片 MD 与基线 README 的定位链接改指该文件；原型页头/抽屉副标题标「当前基线 XX 起步，随迭代扩展」；追加新 REQ 族后多族并存标注（如「v0.5＋47589 两族 REQ」）。「三件同名前缀」此时仅约束 MD 两件。原型入库走 MR 后，回复要带分支与 HEAD 短 sha——用户常拿旧 commit 的文件验收新特性，白报一轮缺陷（实测两次）。任务 MR 开着时用户随时可能点合并：**推后续 commit 前先查 MR state**，发现已 merged 就同分支重开 follow-up MR（diff 对 master 自动只剩合并点之后的新 commit，描述 Refs 原议题）——否则新 commit 挂在已合并 MR 的认知里，交付汇报会漏一件。

输入是已有需求稿（冻结 PRD／docx＋评审回复／基线目录）时：先读完全部原件（含差异与疑点记录），不改写口径，裁决注记（「第一版不做」「往后放」「推到第二期」）照录；开放疑点照录不销项；无独立验收的预留需求在卡片里如实写「验收条款按框架语义验证」，不要编造验收场景。

## 原型技术约束

- 单文件 HTML，vanilla JS，零外部请求（图标库与安全过滤库需内嵌），双击即开断网可用
- `:root` 定义设计 token（色板/字体/间距），用微软雅黑/PingFang SC 栈
- `localStorage` 持久化操作状态，提供 reset 入口
- 角色切换器（至少覆盖 PRD 里的全部适用角色）+ 故障注入开关（success/各异常态），用于验收异常分支
- hash 路由 `#/view/id?type=`，支持分享深链

## 需求编号与功能标注（用户已定）

- 需求编号统一为 **REQ-{需求号}-xxx** 格式（用户已定）：需求号来自外部编号体系（禅道 story 号等，如 47589），卡片序号 xxx 从 01 起连续；如 REQ-47589-01。无外部需求号时用仓内系统代称或日期作需求号段，保持全期唯一、不复用。编号一旦在本期发出，改名要三件同步换（MD＋HTML 全量替换）并跑浏览器回归确认深链/卡片/FAB 徽标都指向新编号
- 原型页面上在相应功能处标注需求编号（.reqtag 徽标）：导航按钮尾部、视图 H2 标题尾部、表格列头、关键控件旁。**徽标文案一律用完整需求号（REQ-47589-01），不用短号（01）或语义短标签（「矩阵」）**——短号在评审时对不上卡片（用户拍板 2026-11-24）
- reqtag 徽标可点击：onclick 调 `locateFromCard(id)`，从页面反向定位到抽屉内该卡片。**页面→抽屉定位契约（五连，缺一即“点了没反应”）**：① 抽屉未开则打开（只切 class，壳不重建）② 清掉会遮住目标的过滤——storyQuery 置空、storyModule 回「全部」（目标卡片可能被活动搜索词或模块 chip 筛掉，不清则定位落空；拍板口径 2026-11-24：点徽标意图是“立刻看到这条需求”，必达优先于保筛选）③ storyOpen=id 展开目标卡片四段式（正文 display 需可见，验收断言含此项）④ 目标卡片滚入抽屉可视区——展开卡片常高于列表视口，`scrollIntoView({block:'center'})` 会把卡头推出视口（实测踩过），改为手动把卡头对齐列表顶部（`list.scrollTop = el.offsetTop - list.offsetTop - 6`） ⑤ 卡片行加高亮描边（≈2s 与定位提示条同寿命）。**列表重绘会替换旧节点：展开/滚动/高亮必须包在 requestAnimationFrame 里重取节点再操作**（实测踩过：同步取到的旧节点随后被 renderStories 替换，操作全部落空——表现为「只开抽屉不开具体卡片」）
- reqtag 徽标嵌在可点击元素（列表行、Tab、按钮）内时，onclick 里必须 `event.stopPropagation()`——否则先触发宿主元素的行点击/视图切换，定位被吞
- **「页面标注」总开关**：抽屉搜索框旁放 checkbox「页面标注」，控制页面上全部 reqtag 徽标的显隐（默认开）；评审演示时可关掉看干净界面，只留抽屉。开关只切 CSS 类（如 body.hide-reqtags .reqtag{display:none}），不重绘页面、不动抽屉内卡片
- 徽标样式：accent-bg 底色 + mono 字体 10px + hover 反色，与 FAB/抽屉同一强调色体系

## 需求卡片弹出面板与双向溯源（核心）

需求卡片做成**右侧滑出式抽屉面板**（drawer），不做独立 tab 页：

- 入口：**右下角悬浮按钮（FAB，fixed 定位）**，内含文档图标＋「需求卡片」文案＋数量徽标；点击弹出抽屉，再点/点轻遮罩/×/Esc 关闭；FAB 常驻不随页面切换消失
- 面板头部：英文眉题（REQUIREMENT CARDS）＋本期标题＋基线日期副信息＋× 关闭按钮，下加浅灰分割线
- 面板主体自上而下：全宽搜索框（按编号/需求/业务规则全文过滤，含验收 GIVEN/WHEN/THEN）→ 横向可滚动模块筛选 chips（全部/各模块，选中态高亮）→ 计数行（N / 总数）→ 卡片列表独立纵向滚动。抽屉骨架（头部/搜索/chips 容器）只建一次，搜索/筛选只重绘列表区容器，chip 选中态切 class 不重建
- 每条卡片一行三列：左侧等宽需求编号（REQ-xxx）＋中间名称与模块/优先级元数据＋右侧圆形定位按钮（▶，stopPropagation）；点击行展开/收起详情（四段式：【1.业务背景】【2.用户故事】【3.功能描述】【4.验收标准】）
- **卡片默认全部折叠**；每次打开抽屉重置全部抽屉状态（展开 storyOpen、搜索词 storyQuery、模块筛选 storyModule 三者都清）；单击卡片行只切换单卡明细的 `display`，**绝不重建抽屉壳**——壳含滑入动画，重建即重放动画、抽屉每点一次闪一次（用户明确反馈过）。任何抽屉内交互要么只改局部 DOM（展开/收起），要么只重绘列表区（搜索/筛选），整页 render() 仅用于打开/关闭抽屉本身
- 数据层：`window.STORIES` 数组，每条需求一个结构化对象，字段含 id/name/module/role/priority/background/userStory/content[]/acceptance[]/extraAnchors[]/requirementSource/原型定位 target（view/id/type/tab/version/action）
- 验收格式：每条验收用 given/when/then 三段式，编号到 `REQ-xxx-ACn` 粒度
- 视觉：面板大圆角（左上/左下）、柔性阴影、轻遮罩（≈8% 黑）；滑入动画 ≈0.2s
- 定位层：`window.Prototype.locate(story)` 接收需求编号，自动完成：切角色 → 跳页面 → 切 tab → 选中版本 → 自动点击目标按钮；**从卡片定位后抽屉保持打开**（用户明确要求，评审时开着抽屉逐条点 ▶、旁边原型页切换对着看），只在底层页面显示定位提示条；操作中途被叫定位时提示先完成当前操作
- **locate() 跳转前必须保留抽屉状态**：若 locate 内部整包替换 `page` 对象，storyOpen/storyQuery/storyModule 会被清掉，抽屉里的展开/搜索/筛选全部丢失——替换前先把这三个字段存出，替换后 Object.assign 赋回
- 深链：`#story=REQ-xxx` 进 hash 时延时调 locate；MD 需求卡片的「定位原型」链接即写此 hash

## 扩充需求与交付验证

向已有原型增加新 REQ（如从 PRD 里补 REQ-002~005）：

1. 从 PRD 原文逐条提取，不改写口径：裁决注记（「第一版不做」「往后放」）照录；验收转 GIVEN/WHEN/THEN，编号到 `REQ-xxx-ACn`
2. 追加 `window.STORIES` 条目，`target` 指向对应页面＋按钮选择器（如 `#btn-upload-tpl`）；目标页面补上该按钮与可操作场景（弹窗/toast 分支：正常、损坏、失败三态都要能演示）
3. FAB 徽标自动随 STORIES 长度；抽屉模块 chips 按新 module 自动分组
4. **徽标覆盖核查（追加族必做）**：逐条新 REQ 断言「在其 target 视图（含被复用的既有视图）上至少有一个 reqtag 徽标」——抽屉里有卡片、▶ 也能跳，但跳到的页面上看不到自己的编号，是追加族最典型的覆盖缺口（新 REQ 常落在既有视图里，而既有视图的徽标只标了旧 REQ）；缺口就往该视图 H2/列头/关键行补徽标。验证走真实用户路径「关抽屉→切 target 视图→点该徽标→卡片展开」，别只查 STORIES 存在性

交付前用浏览器自动化验证（不是靠肉眼）：逐条 `locateFromCard(id)` 后读 `page.view/page.tab`、断言抽屉仍在且未重建（记录壳节点引用比对身份）、抽屉内展开/搜索/筛选状态保持、定位条出现；**再反向逐个点页面上的 reqtag 徽标（含嵌在可点击行/Tab 内的），断言：抽屉打开、壳节点身份不变、目标卡片 `.open` 且 `getBoundingClientRect()` 落在抽屉滚动可视区内、高亮描边出现；带活动搜索词/模块 chip 时点 reqtag，断言过滤被清（storyQuery 空、chip 回「全部」）、目标可见——专防“目标被筛掉、点击像没反应”的洞；页面标注开关关掉后页面 reqtag 全隐、抽屉内卡片不受影响**；再逐场景点按钮验证弹窗/toast/数据副作用（如上传后版本号+1、坏文件不污染数据、reset 可恢复）；故障注入开关下断言按钮禁用态。一次会话内跑完，不留给用户当验收员。验证脚本陷阱：`dispatchEvent(new Event('change'))` 默认不冒泡，document 级委托监听收不到——要传 `{bubbles:true}`；toast 断言前先等旧 toast 消失（3.2s 自动移除）或收集全部 toast 队列再取最后一条，避免读到上一条残留；Python 验证脚本里拼长 JS 字符串易遗括号/引号直接 SyntaxError——拆成多条短 js() 调用更稳。

## 视图与演示数据模式（预留型框架需求适用）

一个导航视图挂多个子页（同 view 不同 tab 承载不同 REQ 族）时，子页必须有**可见页签条**（当前态高亮、可互切），且手动点导航进入该视图时清掉残留 tab 回主表——只靠卡片定位隐式切子页，用户会把「两条 REQ 都定位到同一视图、内容却不同」当 bug 报障；卡片定位（target.tab）与页签条共用同一 tab 状态，定位后页签条当前态要跟上。

只有规则语义、没有页面的预留型需求照样出可交互原型，用四类视图承载：

- **台账视图**：结果/信号列表，每行演示一条冻结件口径，去重键写在标题里；配「数据状态」开关演示三分状态（正常／缺基准→整批数据不足／等待到数→暂无结果）
- **规则库视图**：规则框架表逐条列卡，标注「V1.0 落地／预留」及预留原因（裁决注记放这里）
- **钻取视图**：口径→对象→时刻点三级表，证据字段（实际值/基准/方向幅度/比较符/阈值/规则版本）逐列展示
- **示例播放器视图**：设计示例逐个切换重放，条件类示例做命中矩阵（点条件出✔/✘）；示例文案依赖数据状态开关时必须在 render 时按当前 fault 重建——模块级常量会在首次定义时固化当时的 fault，切开关后不更新（实跑踩过）

演示数据要能对上冻结件示例的数字（区间数、最高值、点数），评审时会被拿原型对着正文核。

## 与架构文档对齐（有架构提案/ADR 时）

目标仓已有架构设计提案、ADR 或裁定记录时，三件套要吸收架构口径，不能只停留在需求语义：

1. 读完全部架构件（提案正文＋裁定/决策点＋修订记录），提取：修改点编号（M-x）、骨架/方案代号、已裁决策及其编号、预留编码/接口名、V1.0 落地→修改点映射表、示例走查结论
2. 需求卡片每张加「架构承接」字段行（需求 → M-x/骨架/既有机制）；卡片背景/功能描述里把已裁口径织入（如「三分语义＝无行/UNDETERMINED/门控行」）；验收可加架构可验条款（如未实现编码启动失败、同键同日互斥）
3. 详细设计：元信息表加「架构依据」行；规则表加架构承接列；落地口径章改成映射表；示例章按架构走查口径标注「V1.0 落地正例 / 属 X 预留」
4. 原型：STORIES 条目加 arch 字段并渲染到卡片表格；页脚与抽屉副标题标架构件版本。区分「需求语义」（冻结件原话）与「架构选择」（提案裁定）——后者标注来源，不冒充需求约束

## 迭代与红旗

- 每轮评审迭代在原文件上追加补丁层（覆写 locate 等入口），保留历史注释标记基线日期
- **三件是双源快照，改一处必查另两处**：需求卡片 MD 与原型 `window.STORIES` 是同一份需求的两个实例（内容、验收、编号），详设改写后两者不会自动跟。每轮详设迭代后：diff 卡片 MD 的四段式与 STORIES 条目（background/userStory/content/acceptance 逐字段），架构口径变更时连 arch 字段一起核；发现漂移以详设为准回填两处
- **迭代前先定位三件套真实位置**：用户会移动目录（说「我移动到了这里」时给的可能只是新基准文档的路径）。用 mdfind/find 按文件名搜全盘确认三件套现址，同名前缀三件应同目录（MD↔HTML 相对链接依赖同目录）；找到后 read_file 全量再改，write_file 有 stale 保护——没读过就整写会被拒，这是提示你先读，不是绕过的信号
- **master 主仓常被其他 worktree 占用**：`git checkout master` 报 "already used by worktree" 时，用 `git worktree add <scratch>/wt-master origin/master` 开独立工作树、在其上建分支干活，push 后 MR 即可；scratch worktree 不会被自动清理，含未合并改动时提醒用户勿删
- 对原型 HTML 做批量文本手术（python 字符串替换）时，定向 replace 与兑底插入两条路径可能都命中造成重复插入——每次插入后 grep -c 验证目标片段出现次数；改完先过**语法门**再进浏览器——抽出 `<script>…</script>` 块写临时文件跑 `node --check`，一个转义错（JS 单引号串内 `\'` 在 python 源码须写 `\\'`，写成 `''` 即语法错）会中断整页脚本，症状是 `S is not defined`/STORIES undefined，浏览器里才显形而 node --check 秒级定位；语法门过后必跑浏览器回归（卡片行数/定位链双向：卡片 ▶→页面＋页面 reqtag→抽屉/视图渲染），不要只看文件写成功
- **热修也要跑同件调查**（prd-source-baseline 一查）：用户报障驱动的原型热修同样先查在途 MR 是否改同一原型/引用文件，再动笔——跳过调查的热修可能与在途分支撞同件（2026-11-24 实况：补查过无冲突，但流程漏了）
- 向原型追加新 REQ 族时，**卡片 MD 与 STORIES 同批落盘**：只做原型不落卡片＝双源快照只剩一源，详设↔卡片↔STORIES 的对账链断掉；用户明示「不用补」时可留欠账，但要在回复里点名欠账清单
- 需求有变更时，三件套同步改：编号不复用，作废需求保留编号并标注作废
- 原型不得宣称未实现的后台能力：纯前端展示的需求卡片如实标注「仅供阅读，无前端触发界面」
- 故障注入开关的每个档位在页脚或开关旁注明对应验收条款编号（如「广东前30日基准缺失→整批数据不足＝REQ-47589-05-AC2」）——评审拿开关演示时能直接对到 AC
