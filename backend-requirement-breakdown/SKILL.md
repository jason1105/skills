# 需求分解

## 目标

补充完整对业务需求的理解，将其拆解为结构化的技术任务列表，并通过持续的问答澄清确保理解无偏差，为后续设计和开发阶段提供清晰的输入。

## 产出物充分性要求

本阶段的产出物是后续所有阶段的起点。**一个不了解业务背景的工程师，读完本文档后必须能够：**

- 理解这个需求要解决什么业务问题
- 知道需要开发哪些功能，每个功能具体做什么
- 清楚功能之间的依赖关系和开发顺序
- 了解技术风险点和应对方案
- 明确什么在范围内、什么不在范围内

## 执行步骤

### ⚠️ Step 0：制定执行计划并和用户确认

**每次执行本 skill 前必须执行此步骤。**

1. 先阅读所有前置文档，理解需求
2. 制定详细的执行计划，包括：
   - 具体步骤
   - 每步做什么
   - 产出物是什么
3. 计划文件保存到：`docs/{需求名}/00-需求分解/00-计划与执行.md`

### Step 4: 把计划展示给用户，确认无误后再开始执行

1. 执行过程中实时更新进度到该文件

计划文件格式：

```markdown
# 需求分解 计划与执行

## 计划
| 步骤 | 内容 | 产出物 |
|------|------|--------|
| 1 | ... | ... |
| 2 | ... | ... |
| ... | ... | ... |

## 进度跟踪
| 步骤 | 状态 | 完成时间 |
|------|------|----------|
| 1 | ⬜ 未开始 | |
| 2 | ⬜ 未开始 | |
| ... | ... | ... |

## 执行日志
### [YYYY-MM-DD]
- 完成了：...
- 遇到的问题：...
- 下一步：...
```

### Step 1: 领域学习

：在分析需求之前，先根据需求涉及的业务领域进行学习。阅读相关领域知识、行业术语、类似系统的设计思路，建立对业务领域的基本理解。这一步是理解需求的前提。

### Step 2: 深入理解需求

：通读用户提供的原型、需求文档或 PRD，提取核心业务目标、涉及的业务实体、关键业务规则。不要浅尝辄止，要逐页、逐条理解。

### Step 3: 澄清模糊点

：列出需求中不明确的点，向用户逐一确认。**只要不是 100% 明白的，必须向用户确认，不做任何假设。** 将所有问题和用户的回答记录到 `需求补充.md` 中。

### Step 4: 识别功能点

：将需求拆解为独立的功能点，每个功能点应满足"可独立开发、可独立测试"。

### Step 5: 分析依赖关系

：标注功能点之间的依赖（哪些必须先做、哪些可以并行）。

### Step 6: 评估复杂度

：对每个功能点标注复杂度（高/中/低），识别技术风险点。

### Step 7: 输出任务列表

：按优先级排序，生成结构化任务表。

### Step 8: Markdown 格式检查

调用 `markdown-lint` skill 对本阶段产出的 Markdown 文档进行格式检查并自动修复。

### Step 9: 用户确认

：将任务列表呈现给用户，确认无遗漏、无误解后写入文件。

### 需求更新时的处理

当需求文档发生更新时：

1. 重新阅读更新后的需求文档
2. 对照 `需求补充.md` 中已有的问答记录，检查是否存在冲突
3. 如有冲突，**必须向用户确认以哪个为准**，并更新 `需求补充.md`
4. 根据变更情况更新需求分解文档

## 输入输出

- 输入：业务需求描述（自然语言、PRD 文档、原型、用户故事等）
- 输出：
  - `docs/{需求名}/00-需求分解/00-需求分解.md` — 结构化技术任务列表
  - `docs/{需求名}/00-需求分解/需求补充.md` — 问答澄清记录

## 安全风险识别
识别需求中涉及的安全敏感场景，提前规划防护重点。至少检查以下维度：

| 维度 | 检查项 | 本需求是否涉及 | 安全关注点 |
|------|--------|----------------|-----------|
| 用户数据 | 是否处理用户个人信息（姓名、手机、身份证、住址等） | 是/否 | 加密存储 + 展示脱敏 + 访问审计 |
| 认证授权 | 是否涉及登录、权限分配、角色管理 | 是/否 | 防暴力破解 + 越权检查 + 多因素鉴别 |
| 支付/交易 | 是否涉及金额、支付、订单 | 是/否 | 金额服务端计算 + 幂等性 + 防重放 |
| 文件处理 | 是否涉及文件上传/下载 | 是/否 | 类型白名单 + 大小限制 + 路径规范化 |
| 外部集成 | 是否调用第三方 API 或被第三方调用 | 是/否 | 认证凭证管理 + SSRF 防护 + 输入校验 |
| 数据导出 | 是否提供数据导出/批量查询 | 是/否 | 导出权限校验 + 频率限制 + 审计留痕 |
| 业务状态流转 | 是否有审批、状态变更流程 | 是/否 | 状态机校验 + 操作审批分离 |
| 等保合规 | 项目是否需要等保测评（二级/三级） | 是/否 | 参考 `security/compliance-testcases.md` |

> 识别为"是"的项，会在详细设计阶段结合 `security/security-features.md` 和 `penetration-defense.md` 做具体的安全架构设计。

## 验收标准

- [ ] 执行计划已制定且用户已确认（Step 0）
- [ ] 领域知识已学习，关键概念记录在文档中
- [ ] 所有功能点满足"可独立开发、可独立测试"
- [ ] 模糊点已全部向用户澄清，问答记录在 `需求补充.md` 中
- [ ] 依赖关系无循环
- [ ] 技术风险点已识别并有具体应对方案（不是"待定"）
- [ ] 安全风险识别完成，识别为"是"的维度已明确将在详细设计阶段处理
- [ ] 需求边界清晰，"不包含"部分已明确
- [ ] 产出物充分性自检通过：一个新工程师能仅凭文档理解全部需求

## 注意事项

- **只要不是 100% 明白的，必须向用户确认，绝不假设**
- 功能点粒度适中：太粗则无法指导开发，太细则增加管理成本
- 优先级由业务价值和技术依赖共同决定
- 功能点的"详细描述"不能只写一句话，要具体到工程师能理解做什么
- `需求补充.md` 是活文档，贯穿整个研发周期，后续阶段如有新的澄清也应追加记录
- **跨 skill 引用**：执行本 skill 时可引用其他已存在的 skill 来补充能力；用户对 skill 使用有明确偏好时，优先满足用户偏好（详见 `backend-dev/SKILL.md` 「跨 Skill 引用与协作原则」）
