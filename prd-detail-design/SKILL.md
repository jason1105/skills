# PRD 需求详细设计生成规范

## When to Use

- 用户要求「出需求详细设计／PRD 详设／产品需求详细设计」或给一份需求稿要成文
- 已有详设需要迭代（吸收架构提案/ADR/新裁决）
- 输入形态任意：冻结 docx＋评审回复、基线目录（00-来源记录/02-解析/03-差异与疑点）、口述、旧版 PRD
- 详设完成后，后续「需求卡片＋可交互原型」由姊妹 skill `prd-interactive-prototype` 承接（详设是它的输入）

## 样本与规范

- 结构样本：Market 详细设计（`~/Downloads/AI Agent 智能体/Market 系统详细设计+可交互原型/Market_产品需求详细设计.md`；被移动时 mdfind -name "Market_产品需求详细设计"）——章节骨架与功能点七段式见 `references/structure.md` 与 `references/feature-anatomy.md`
- 写作规范：《PRD编写规则》（`prd-review/rules/PRD编写规则.md`，唯一现行规范；《PRD编写规范》已停用不用）。本 skill 正本在仓库 `~/.agents/skills/prd-detail-design/`（随 skills 仓迁入 ~/.agents；旧路径 ~/MyProjects/lvwei/ai/skills 已废）（改动：仓库编辑 → `npx skills add <仓库> -g --skill prd-detail-design` 装回 → commit/push）

## 生成流程

1. **读完全部输入原件**：冻结正文、评审回复、差异与疑点记录、既有架构提案/ADR（有则同时吸收，见第 4 步）；docx 用 python zipfile 抽 word/document.xml 文本。基线目录已有 prd-parser 产出的《NN-需求结构化基准.md》时它是第 2 等输入（仅次于冻结原件）：F/BR/E/实体/疑点五类直接映射到功能总览表/业务规则/异常流/属性表/待确认附录，但成文时逐条回核冻结件出处，不从基准件抄转述
2. **定编号体系**：REQ-{需求号}-xxx（用户已定；需求号来自禅道 story 等外部体系，无则用系统代称/日期占位），全期唯一不复用，文头声明「REQ-xxx～REQ-xxx 为本期评审、原型批注和验收的唯一功能编号」
3. **按骨架成文**（章节表见 references/structure.md）：文头（基线/修订日期＋评审受众＋范围声明）→ 第一章概述（背景目标/核心场景表/相关角色表/业务流程图）→ 每功能模块一章（模块说明→用户旅程 J-xx→页面布局→功能总览表→功能点描述→页级异常文案）→ 权限矩阵章 → 非功能+端到端验收章 → 附录六件（术语/业务对象/状态流转/待确认/不纳入/资料来源）
4. **有架构提案/ADR 时吸收架构口径**：元信息表加「架构依据」行；规则/能力表加架构承接列；落地口径章写成映射表；区分「需求语义」（冻结件原话）与「架构选择」（裁定），后者标注来源不冒充需求约束
5. **预留型需求降维**：无页面的框架级需求（规则语义/预留条件）不编造页面，用规则框架表＋落地/预留列＋映射表＋示例走查承载；验收如实写「按框架语义验证，无独立验收场景」，见 references/structure.md 末节
6. **开发中需求吸收实施计划**（有架构提案＋配套实施计划＋任务 MR 在跑时，实施计划是第一等输入）三件必收：①**行为真值表**（门控/策略/事件写入共用的输入→行为规格）并入对应功能点作「判定细则」，验收条款逐行补断言（每行=一条 AC：输入组合→哪些调用发生/不发生）；②**分层检测流程**（细分对象按值检测→逻辑对象按成员结论判定→聚合）写成独立用户旅程＋「策略等价表」（两类策略的接口/输入/输出/实现/配置/调用点对照，明写后者的策略角色=前者的检测策略）；③**任务状态映射表**（已并 master/在途 MR/待启动三态映射到 REQ 编号）放附录不进正文（开发进度是易变事实），登记滚动更新义务：后续任务 MR 合并后更新状态列，语义级变化同步迭代对应 REQ 小节。用户旅程写主线动作（业务上要做的事）为主，反向分支（「不建则如何」）降为分支备注——主线被分支喧宾夺主会被评审打回

7. **落地路径分析（用户要「47848 怎么落地」类问题时）**：BR 逐条承载核对表是核心论证手法——结构化基准的每条 BR 对到「框架既有能力/框架在途任务/宿主配置/前端页面/纯语义约束」五类，若框架侧全被既有＋在途任务接走则结论＝「该需求零专属编码任务」，活集中在配置/页面/验收三处；产出形式为仓内提案＋实施计划两件套（见下），详设不重复承载此内容、只在文头或附录引用提案定位

## 提案＋实施计划产出（仓有 80-提案与计划 目录惯例时）

落地路径分析若需成件，按《实施计划规范》（研发规范库）出**同前缀配对两件**：`NN-<事项名>提案.md`（做法，不含时间，含 BR 承载核对表＋修改点 M-x＋验收场景映射＋依赖图＋拍板项 P-x 表）＋ `NN-<事项名>实施计划.md`（任务，必带时间/人日/负责人，跟踪图按三色画法 done/todo/hold，交付物表含回写行）。要点：
- 编号取夹内 max+1，**动笔前查在途 MR 是否新增 80 夹文件**（占号冲突）
- 落状态机：提案「做法待批准」→批后升 v0.5→实施计划「任务待批准」→批后 v1.0（两次批准流程）；MR 描述带 Closes/Refs 议题号
- 修改点里区分「本仓任务」与「外部依赖任务」（他仓实施计划跟踪的），外部依赖在跟踪图用 hold 虚线＋标注归属
- 拍板项不代答：每个 P-x 给推荐项＋备选项，批准时一并定

## 铁律

- 不改写冻结口径：裁决注记（「第一版不做」「往后放」「推到第二期」）照录；开放疑点照录不销项、不代答
- 疑点处置列禁止跨文件编号缩写（如「随⑨评审逐项过(07号§9)」「同上」）——读者无法解码；一律直指本目录文件：「登记于 03-差异与疑点 疑点 N，随基线评审逐项确认」，溯源尾注可留（原⑨）
- **架构造词进详设前先与用户对齐定义**：架构文档自创的复合缩写（如「成员口径」）把配置层引用/运行层实体/判定层输入三个粒度压进一个词，用户拿业务定义质询（「成员应该是 X」）时先拆词对位再写文；用户给出精确定义（如「细分指标对象＝定义+口径+周期+监测对象+具体数值」）后按其定义改写全部相关表述，并连锁修正受影响 REQ 小节、术语表与原型文案——留着旧复合词评审必被再问一轮
- 演示/示例数字必须对上冻结件原文（区间数、最高值、点数）——评审会拿文对文核
- 表内字段口径唯一：同一字段在总览表/功能点/属性表里名称、取值、默认值三处一致
- **同批需求重叠区只写一遍**：同批冻结的多份需求常有大段近逐字复写（通用框架层与项目落地层各写一次同一语义，句级比对可见）。详设对重叠区引用不复制——锚定到裁定侧（评审裁定指定以哪份为准时按其锚，如门控语义锚在落地需求、框架语义锚在预留需求），非锚定侧详设只写「语义见 REQ-xxx，本项目取值见本文」式引用＋一条指回锚定需求的钩子（防评审问「某扩展项哪去了」类漏项）；两边都全文重写，后续任一侧修订即漂移
- 输出为单个 `{系统}_产品需求详细设计.md`，与后续卡片/原型同名前缀同目录（相对链接依赖同目录）。原型被用户定为「全仓唯一持续迭代」时，详设/卡片仍按基线目录各自成件（`{阶段}基线/NN-产品需求详细设计.md`），只有原型共享——详设是阶段冻结件，不跟着原型跨阶段滚
- **回溯型基线（开发完成后补详设）**：实现侧也是输入——框架仓/宿主仓的代码与设计文档（指定 commit/分支）用来写「实现落点」映射表与「v0.x 实际接入清单」；状态列写已实现/预留的**实际值**而非计划值；验收仍写成 GIVEN/WHEN/THEN 应然语义供回归，不冒充当年实测证据。基线目录里放来源记录（九类输入：现行需求件/归档/原始资料/听记/两仓代码）+需求梳理（规则逐条可验）+详设三件打底

## 迭代

- 迭代前先定位真实位置（用户会移动目录）：mdfind/find 按文件名搜，找到后 read_file 全量再改
- 需求变更时编号不复用，作废需求保留编号并标注作废
- 吸收新裁决时受影响章节同步改，修订记录行追加依据
