## API 通用约定

### 统一响应格式

```json
{
  "code": 200,
  "message": "操作成功",
  "data": { }
}
```

### 分页请求

```
GET /api/v1/资源?pageNum=1&pageSize=10&orderBy=createTime&order=desc
```

### 分页响应

```json
{
  "code": 200,
  "message": "操作成功",
  "data": {
    "list": [],
    "total": 100,
    "pageNum": 1,
    "pageSize": 10,
    "pages": 10
  }
}
```

### 错误码规范

| 段位 | 范围 | 说明 |
|------|------|------|
| 通用 | 200, 400-499, 500-599 | HTTP 标准状态码 |
| 业务 | 1000-1999 | 通用业务错误 |
| 模块 A | 2000-2999 | 模块 A 专用 |
| 模块 B | 3000-3999 | 模块 B 专用 |
| ... | 按模块递增 | ... |

### RESTful 路径规范

| 操作 | 方法 | 路径 | 示例 |
|------|------|------|------|
| 列表查询 | GET | /api/v1/{资源}s | /api/v1/users |
| 详情查询 | GET | /api/v1/{资源}s/{id} | /api/v1/users/1 |
| 新增 | POST | /api/v1/{资源}s | /api/v1/users |
| 修改 | PUT | /api/v1/{资源}s/{id} | /api/v1/users/1 |
| 删除 | DELETE | /api/v1/{资源}s/{id} | /api/v1/users/1 |
| 批量操作 | POST | /api/v1/{资源}s/batch-{动作} | /api/v1/users/batch-delete |

### 版本管理策略

API 需要演进但不能破坏已有调用方。常见版本管理方式有三种，选一种并在文档中明确：

| 方式 | 示例 | 优点 | 缺点 |
|------|------|------|------|
| **URL 路径** | `/api/v1/users` → `/api/v2/users` | 直观，易调试 | URL 变化 |
| **请求头** | `Accept: application/vnd.api+json;version=2` | URL 稳定 | 调试不直观 |
| **查询参数** | `/api/users?version=2` | 实现简单 | 不规范，不推荐 |

**推荐使用 URL 路径方式**。

**版本迭代规则**：

- **向后兼容变更**（新增字段、新增可选参数、新增接口）→ 不升级主版本，可直接改 v1
- **破坏性变更**（删除字段、修改字段类型、修改响应结构、删除接口、必填参数变更）→ 升级主版本（v1 → v2），旧版本保留至少一个迭代周期后废弃
- **废弃通知**：接口废弃前，在响应头加 `X-API-Deprecated: true` 和 `X-API-Sunset-Date: YYYY-MM-DD`

**版本迁移文档**：每次升级主版本时，在 API 设计文档中增加一节"vN → vN+1 迁移指南"，列出所有变更点及迁移方法。

### 异步接口设计

对于耗时较长或需要实时推送的场景，需要设计异步接口。选用合适的模式：

#### 模式 1：长任务轮询（最常用）

适用于：数据导出、批量处理、报表生成等耗时操作。

```
POST /api/v1/exports               → 创建任务，返回 taskId
GET  /api/v1/exports/{taskId}      → 查询任务状态
GET  /api/v1/exports/{taskId}/result → 获取结果（仅任务完成后）
```

任务状态字段：

```json
{
  "taskId": "uuid",
  "status": "PENDING",  // PENDING / RUNNING / SUCCESS / FAILED
  "progress": 35,        // 百分比
  "createTime": "...",
  "finishTime": null,
  "errorMessage": null,
  "resultUrl": null      // 仅 SUCCESS 时有值
}
```

#### 模式 2：WebSocket 实时推送

适用于：实时通知、在线协作、实时监控数据。

```
WebSocket 连接地址：ws://host/api/v1/ws/{topic}
鉴权方式：[URL 参数 token / 连接后首条消息鉴权 / Cookie]
消息格式：JSON，字段 { type, payload, timestamp }
心跳机制：客户端每 30 秒发送 ping，服务端回 pong；60 秒无心跳断开
```

#### 模式 3：Server-Sent Events（SSE）

适用于：单向推送、进度更新、流式响应。

```
GET /api/v1/stream/{taskId}
Accept: text/event-stream
```

#### 模式 4：Webhook 回调

适用于：第三方集成，事件触发后通知调用方。

```
POST 【调用方注册的 URL】
Headers:
  X-Signature: HMAC-SHA256 签名（防伪造）
  X-Event-Type: event.name
Body: JSON
```

**异步接口设计要点**：

- 所有异步操作必须可追踪状态（taskId、requestId）
- 超时处理：长任务设置最大执行时间，超时标记为失败
- 幂等性：重复提交同一任务应返回已有 taskId，不重复执行
- 回调失败重试：Webhook 失败时按策略重试（如指数退避 3 次）

## 注意事项

- URL 路径使用小写中划线，如 `/api/v1/user-roles`
- 请求/响应字段使用 camelCase
- 枚举值在文档中明确列出所有可选值及含义
- 复杂查询可使用 POST 替代 GET，路径加 `/search` 后缀
- 响应体示例中的每个字段都要加注释说明
- **跨 skill 引用**：执行本 skill 时可引用其他已存在的 skill 来补充能力；用户对 skill 使用有明确偏好时，优先满足用户偏好（详见 `backend-dev/SKILL.md` 「跨 Skill 引用与协作原则」）

## 已知陷阱

- **设计文档只写业务语义，不写实现细节**：字段描述、枚举值说明、响应示例中的注释均使用中文业务语言（如"省间联络线计划96点"），不出现具体变量命名、英文技术术语或实现层的字段名。设计文档面向业务理解，字段命名属于实现关注点，不应渗入设计文档。
