# 沉淀

## 目标

整理后端研发全流程各阶段的产出物，生成一份交付物总览文档，方便团队成员快速了解项目全貌和各阶段成果。

## 产出物充分性要求

**一个项目经理或新加入的工程师拿到本文档后必须能够：**

- 在 5 分钟内了解这个需求做了什么、产出了什么
- 快速找到任意阶段的详细文档
- 了解当前的质量状况和遗留问题
- 知道后续还需要做什么

## 前置条件

- 阶段 0-4 的产出物文件已存在（至少大部分已完成）

## 执行步骤

### ⚠️ Step 0：制定执行计划并和用户确认

**每次执行本 skill 前必须执行此步骤。**

1. 先阅读所有前置文档，理解需求
2. 制定详细的执行计划，包括：
   - 具体步骤
   - 每步做什么
   - 产出物是什么
3. 计划文件保存到：`docs/{需求名}/06-交付物总览/00-计划与执行.md`

### Step 4: 把计划展示给用户，确认无误后再开始执行

1. 执行过程中实时更新进度到该文件

计划文件格式：

```markdown
# 交付物沉淀 计划与执行

## 计划
| 步骤 | 内容 | 产出物 |
|------|------|--------|
| 1 | ... | ... |
| 2 | ... | ... |
| ... | ... | ... |

## 进度跟踪
| 步骤 | 状态 | 完成时间 |
|------|------|----------|
| 1 | ⬜ 未开始 | |
| 2 | ⬜ 未开始 | |
| ... | ... | ... |

## 执行日志
### [YYYY-MM-DD]
- 完成了：...
- 遇到的问题：...
- 下一步：...
```

### Step 1: 扫描产出物目录

：检查 `docs/{需求名}/` 下各阶段子目录的文件完整性。

### Step 2: 提取各阶段摘要

：从每个阶段的产出物中提取核心信息摘要。

### Step 3: 统计代码产出

：统计实现阶段产出的代码文件数量、类数量等。

### Step 4: 汇总验证结果

：从验证报告中提取通过率和遗留问题。

### Step 5: 生成交付物总览

：将所有信息汇总为结构化文档。

### Step 6: 更新 PROGRESS.md

：将所有阶段状态标记为最终状态。

### Step 7: Markdown 格式检查

调用 `markdown-lint` skill 对本阶段产出的 Markdown 文档进行格式检查并自动修复。

### Step 8: 用户确认

：将总览文档呈现给用户，确认后写入文件。

- 输入：`docs/{需求名}/` 目录下所有阶段的产出物

## 技术债务清单

未偿还的技术债务，明确记录便于后续迭代处理。不要隐藏，不要美化。

| 编号 | 类型 | 描述 | 产生原因 | 影响 | 偿还成本 | 偿还建议 |
|------|------|------|---------|------|----------|---------|
| TD-01 | 代码 | [具体的技术债务] | [为什么当时没做/没做好] | [不处理会怎样] | 小/中/大 | [如何偿还] |

**技术债务类型参考**：

| 类型 | 典型场景 |
|------|---------|
| 代码债务 | Mock 实现未替换为真实实现、TODO 未完成、临时兜底代码 |
| 测试债务 | 单元测试覆盖不全、缺少集成测试、缺少性能测试 |
| 文档债务 | 文档与代码不一致、缺少运维文档 |
| 架构债务 | 分层不清晰、模块耦合过高、临时方案未重构 |
| 安全债务 | 已识别但未修复的安全问题（低危）、依赖库版本陈旧 |
| 性能债务 | 已知性能瓶颈但当前未优化、N+1 查询等 |
| 依赖债务 | 依赖的上游接口不稳定、使用了内部/废弃 API |

## 验收标准

- [ ] 执行计划已制定且用户已确认（Step 0）

- [ ] 遗留问题已汇总，有具体的处理建议和时限

- [ ] **技术债务清单**已列出，每项标注类型、原因、影响、偿还建议
- [ ] **后续迭代建议**已按 P0/P1/P2/P3 优先级分类
- [ ] 接口清单和表清单完整
- [ ] `docs/{需求名}/PROGRESS.md` 已更新为最终状态
- [ ] 产出物充分性自检通过：项目经理可在 5 分钟内了解全貌
- [ ] `docs/知识沉淀/` 目录下的技术知识文档已在总览中列出（框架用法、依赖关系、设计约束等），每篇文档标注主题和收益
- [ ] 产出文档末尾含「修订记录」章节：新建记 v0.1；后续迭代只追加行，不改历史行

## 注意事项

- 跳过的阶段在总览中标注"⏭️ 跳过"及跳过原因
- 遗留问题从验证报告中提取，不重复分析
- 后续建议要具体可执行，不是泛泛的"持续优化"
- 数字要准确，从各阶段文档中实际统计，不要估算
- **跨 skill 引用**：执行本 skill 时可引用其他已存在的 skill 来补充能力；用户对 skill 使用有明确偏好时，优先满足用户偏好（详见 `backend-dev/SKILL.md` 「跨 Skill 引用与协作原则」）
- **修订记录**：产出文档末尾加「修订记录」章节，格式 `| 版本 | 日期 | 变更人 | 变更说明 |`；新建记 `v0.1 | YYYY-MM-DD | 作者 | 初稿`，后续修改只追加行
