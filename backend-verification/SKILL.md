# 验证

## 目标

对编码实现阶段的产出进行系统性验证，覆盖功能正确性、边界条件、异常处理，生成结构化的验证报告。

## 产出物充分性要求

**一个 QA 工程师或后端工程师拿到本文档后必须能够：**

- 理解每个测试用例在验证什么业务场景
- 根据测试用例的输入和期望结果独立复现测试
- 清楚当前的质量状况（通过率、遗留问题）
- 了解每个遗留问题的严重程度和影响范围
- 判断是否可以进入下一阶段

## 前置条件

- `docs/{需求名}/04-实现记录/04-实现记录.md` 已存在
- 代码文件已完成编写

### Step 1：确定验证方式

开始前先决定采用哪种验证方式，并在报告中明确标注：

| 方式 | 适用场景 | 结果标注 |
|------|---------|---------|
| **实际运行测试** | 代码可以编译运行、测试环境可用 | 记录真实的接口返回、耗时、错误日志 |
| **代码走读（Code Review）** | 无法运行代码（环境不可达、依赖缺失、仅审查代码）| 标注"[代码走读]"，仅基于代码推理给出结论 |
| **混合方式** | 部分能运行、部分只能审查 | 每个用例标注采用哪种方式 |

**优先级**：能实际运行就不用走读。代码走读无法发现运行时问题（性能、并发、实际网络行为），结果可信度低于实际运行。

### Step 2：阅读实现记录

从实现记录获取实现范围、代码结构、已知偏差、TODO 清单。

### Step 3：回顾设计文档

对照 API 接口设计和详细设计，提取验证要点。

### Step 4：检查单元测试

验证实现阶段产出的单元测试是否覆盖所有 Service 方法，是否包含正常、边界、异常场景。

### Step 5：设计接口测试用例（功能测试）

为每个接口设计以下三类测试用例：

- **正常流程**：标准输入、期望输出，覆盖主要业务场景
- **边界场景**：空值、极值、特殊字符、超长输入、并发
- **异常场景**：无权限、资源不存在、参数格式错误、业务规则冲突

### Step 6：设计集成测试用例

单元测试验证单个方法，集成测试验证模块间协作。覆盖以下场景：

| 场景类型 | 验证什么 |
|---------|---------|
| 端到端流程 | 从 HTTP 请求到数据库落库的完整链路 |
| 跨模块协作 | 模块 A 调用模块 B，模块 B 的行为是否符合契约 |
| 事务边界 | 跨多个操作时，部分失败是否正确回滚 |
| 异步流程 | 消息生产→消费、任务触发→完成的完整链路 |
| 第三方集成 | 外部服务调用的成功、失败、超时、重试行为 |

**集成测试与单元测试的关系**：

- 单元测试 Mock 掉外部依赖，只测本类/本方法
- 集成测试尽量用真实依赖（或测试替身如内存数据库），测协作关系

### Step 7：设计性能测试用例（关键接口）

对关键接口（首页加载、核心业务、高频调用）做性能测试。其他接口可按需选做。

**性能指标**：

| 指标 | 说明 | 参考阈值 |
|------|------|---------|
| 响应时间 | 单次请求从发送到收到响应的耗时 | P99 < 1s、P50 < 300ms（具体值按业务要求） |
| 吞吐量（QPS/TPS） | 单位时间能处理的请求数 | 按并发用户数和业务规模评估 |
| 并发能力 | 同时能承受的并发连接数 | 至少能撑住日常峰值的 3 倍 |
| 错误率 | 压测下的失败率 | < 0.1% |
| 资源占用 | CPU、内存、数据库连接池在压测下的使用情况 | 不出现耗尽 |

**性能测试方法**：

- 工具示例：JMeter、wrk、Gatling、Locust 等（按项目选择）
- 场景：基准测试（正常负载）、压力测试（逐步加压找瓶颈）、稳定性测试（长时间运行）
- 阈值由详细设计的"非功能性要求"章节确定，验证时对照

**代码走读场景下**：无法做真实性能测试，可从代码推导潜在性能问题（N+1 查询、大循环、未加索引的查询、同步阻塞调用等），标注"[代码走读] 潜在性能风险"。

### Step 8：执行验证

逐条执行测试用例，记录实际结果。运行单元测试并记录通过率。运行集成测试和性能测试（如适用）。

### Step 9：安全合规验证

阅读 `backend-dev/references/security/compliance-testcases.md` 和 `penetration-defense.md`，对照等保测试用例检查系统是否满足安全功能要求和渗透防护要求。将安全相关的验证结果单独列出。

### Step 10：标记问题

发现的问题标记为 Bug / 改进建议 / 待确认，**每个问题必须说明影响范围和复现步骤**。

### Step 11：生成验证报告

汇总所有测试用例及结果。

### Step 12：Markdown 格式检查

调用 `markdown-lint` skill 对本阶段产出的 Markdown 文档进行格式检查并自动修复。

### Step 13：用户确认

将验证报告呈现给用户，确认后写入文件。

## 验收标准

- [ ] 执行计划已制定且用户已确认（Step 0）
- [ ] 验证方式已在报告中明确标注（实际运行 / 代码走读 / 混合）
- [ ] 每个 API 接口至少有 3 个功能测试用例（正常 + 边界 + 异常各至少 1 个）
- [ ] 单元测试覆盖所有 Service 方法，通过率已记录
- [ ] 集成测试覆盖端到端流程、跨模块协作、异步流程等关键场景
- [ ] 关键接口已做性能测试，或（代码走读场景下）已识别潜在性能风险
- [ ] 安全合规验证已对照 `compliance-testcases.md` 执行，结果已记录
- [ ] 所有测试用例都有具体的输入和期望结果（不是"正常返回"）
- [ ] API 接口设计中定义的所有错误码都有对应的测试用例
- [ ] 发现的问题都有影响范围和复现步骤
- [ ] 验证结论明确，可进入/不可进入下一阶段有清晰判断
- [ ] 产出物充分性自检通过：QA 可按文档独立复现所有测试

## 注意事项

- 测试用例的"输入"和"期望结果"必须是具体值，不是描述性文字
- 边界场景重点关注：空字符串、null、0、负数、超长字符串、SQL 特殊字符
- 如无法实际运行代码，进行代码走读（Code Review）形式的静态验证，标注"[代码走读]"
- 验证报告中的结论要给出明确的"是否可进入下一阶段"判断
- **跨 skill 引用**：执行本 skill 时可引用其他已存在的 skill 来补充能力；用户对 skill 使用有明确偏好时，优先满足用户偏好（详见 `backend-dev/SKILL.md` 「跨 Skill 引用与协作原则」）
