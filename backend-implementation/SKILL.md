# 编码实现

## 目标

按照需求分解、详细设计、DDL 设计、API 接口设计的产出物，编写符合编码规范的后端代码，并记录实现过程中的关键决策。

## 产出物充分性要求

**一个接手项目的工程师拿到实现记录和代码后必须能够：**

- 理解代码的整体结构和各模块职责
- 知道代码与设计文档的对应关系，以及偏差的原因
- 了解使用了哪些第三方库、为什么选择它们
- 快速定位需要修改的代码位置
- 理解实现中的特殊处理和注意事项
- 即使实现被中断，也能根据研发计划恢复进度

## 前置条件

- `docs/{需求名}/00-需求分解/00-需求分解.md` 已存在
- `docs/{需求名}/01-详细设计/01-详细设计.md` 已存在
- `docs/{需求名}/02-DDL设计/02-DDL设计.md` 已存在
- `docs/{需求名}/03-API接口设计/03-API接口设计.md` 已存在

## 执行步骤

### ⚠️ Step 0：制定执行计划并和用户确认

**每次执行本 skill 前必须执行此步骤。**

1. 先阅读所有前置文档，理解需求
2. 制定详细的执行计划，包括：
   - 具体步骤
   - 每步做什么
   - 产出物是什么
3. 计划文件保存到：`docs/{需求名}/04-实现记录/00-计划与执行.md`
4. **把计划展示给用户，确认无误后再开始执行**
5. 执行过程中实时更新进度到该文件

### ⚠️ Step 1：编码规范确认（强制检查，不可跳过）

**每次执行本 skill 前必须执行此步骤。**

```
检查 references/coding-standards.md 是否存在
├── 存在 → 阅读规范内容，在后续编码中严格遵循
└── 不存在 → 强制暂停，向用户报告：
    "编码规范文件 references/coding-standards.md 不存在。
     请提供你的编码规范（可以是文档、链接或直接描述），
     我会保存到 references/coding-standards.md 供本次及后续使用。"
    等待用户提供后，保存到 references/coding-standards.md，再继续。
```

**此步骤不可跳过、不可用默认规范替代。** 编码规范由用户/团队定义，不同项目可能完全不同。

### Step 2：阅读所有设计文档

依次阅读以下文档，建立完整的上下文理解：

1. 需求分解 + 需求补充 — 理解业务目标和功能点
2. 详细设计 — 理解模块划分和流程
3. DDL 设计 — 理解数据结构
4. API 接口设计 — 理解接口契约
5. 编码规范 — 理解代码风格要求
6. **安全编码规范** — 阅读 `backend-dev/references/security/secure-coding.md`，理解 16 类代码安全漏洞及修复对策，编码过程中逐条对照

### Step 3：确认技术实现细节

以下细节如果在详细设计或编码规范中未明确，**必须向用户确认**后再开始编码：

| 需确认项 | 示例 |
|----------|------|
| 项目结构约定 | 是否使用构建子模块？还是文件夹区分模块？ |
| 双实现切换机制 | 通过配置文件、环境变量、还是条件注解切换？ |
| 测试框架 | 使用什么单元测试框架？ |
| 数据库兼容性 | 目标数据库的语法特性、分页方式、函数差异？ |
| 配置管理方式 | 配置文件格式、配置中心？ |

已在设计文档或编码规范中明确的内容无需重复确认。

### Step 4：创建特性分支

以 `proj/dev` 分支为基础，创建新的特性分支进行开发：

```bash
git checkout proj/dev
git pull
git checkout -b feat/{需求名简称}
```

分支命名使用英文小写 + 中划线，如 `feat/user-permission`、`feat/order-export`。

在开始编码之前，先生成执行计划文档，便于跟踪实现过程。**即使遇到意外被中断也能根据计划恢复。**

计划文件存放在：`docs/{需求名}/04-实现记录/00-计划与执行.md`

### Step 6：确定实现顺序

按依赖关系排列实现顺序，通常为：

1. 实体/模型类（Entity / Model）
2. 数据访问层（Mapper / Repository / DAO）
3. 业务逻辑层（Service + 实现类）
4. 控制器层（Controller / Handler）
5. 数据传输对象（DTO / VO）
6. 配置类、工具类
7. 异常处理
8. 单元测试

具体的分层方式和命名以项目的编码规范和详细设计为准。

### Step 7：逐模块编码

对每个模块：

1. 按 Step 5 的顺序创建各层代码
2. 遵循 `references/coding-standards.md` 中的规范
3. 每个类/方法/函数添加注释说明
4. 遵循详细设计中的异常处理策略
5. 遵循 API 接口设计中的请求/响应格式

**双实现模式**：因为项目初期可能还没有真实数据，须提供两套业务逻辑实现。

#### 何时使用 Mock 实现

| 场景 | 说明 |
|------|------|
| 项目初期数据库未就绪 | 后端先行，前端可基于 Mock 开始联调 |
| 依赖的上游接口未完成 | 上游未就绪时，用 Mock 模拟上游响应，不阻塞下游开发 |
| 演示/评审用 | 早期演示给客户看效果，无需等待真实数据 |
| 单元测试 | Mock 实现可作为部分测试用例的基准 |

Mock 实现**仅在开发和测试环境启用**，生产环境必须使用真实实现。

#### 如何切换

切换机制需要满足：同一份代码可以在不同环境跑出不同行为，部署时无需改代码。具体方式在 Step 2 中与用户确认，常见三种：

| 方式 | 说明 | 示例 |
|------|------|------|
| 配置开关 | 在配置文件中声明使用哪个实现 | `service.impl=mock` 或 `service.impl=real` |
| 环境变量 | 通过环境变量控制 | `SERVICE_IMPL=mock` |
| Profile / 条件加载 | 按运行环境自动选择 | dev 环境用 Mock，其余用真实实现 |

切换必须**做到只改配置不动代码**。

#### Mock 实现规范

- 命名：在真实实现类名后加 `Mock` 后缀（如 `OrderServiceMockImpl`），或放在独立包/目录下
- 数据：硬编码返回值，尽量贴近真实业务场景（字段完整、数值合理）
- 注释：类头部必须标注"Mock 实现，仅供开发/测试使用"
- 边界：模拟少量异常场景（如返回空列表、模拟超时），便于前端测试异常分支

#### 真实实现的 TODO 标记规范

真实实现初期可能留空，但必须遵循以下规范：

- 方法体不能完全空实现——至少抛出 `UnsupportedOperationException` 或等价异常
- 方法头部必须有 `TODO` 注释，说明**还需要做什么**以及**由谁负责**：

```
// TODO(张三, 2026-05-01): 替换为真实的数据库查询
// 依赖：t_order 表已建好
// 参考：详细设计 > 订单模块 > 订单查询流程
```

- TODO 必须有**责任人**和**预计完成时间**，不接受没有时间的 TODO
- 所有 TODO 在研发计划中单独列一节"待补全清单"跟踪，不能遗留到验证阶段

### Step 8：编写单元测试

**代码必须有单元测试。** 对每个业务逻辑方法编写至少覆盖以下场景的测试用例：

- 正常入参，验证返回值
- 边界入参（空值、极值）
- 异常场景（业务规则违反、数据不存在）

单元测试应同时覆盖 Mock 实现和真实实现（真实实现的 TODO 方法可用"预期抛出 UnsupportedOperationException"作为断言）。

### Step 9：编码安全自检

编码完成后，对照 `backend-dev/references/security/secure-coding.md` 末尾的"编码自检清单"逐条检查，确保不存在已知安全漏洞。未通过项必须修复后再进入下一步。

### Step 10：代码审查自查

提交代码审查前，开发者先对照以下清单自查，减少审查轮次：

**功能性**

- [ ] 所有设计文档中的功能点都有对应实现（或标注 TODO + 责任人 + 时间）
- [ ] 异常路径都有处理，无未捕获的异常逸出
- [ ] 边界条件（空值、0、最大值、并发）已考虑

**可读性**

- [ ] 类/方法/变量命名清晰，无缩写歧义
- [ ] **所有公共类、接口、方法必须有完整的Javadoc注释**
- [ ] **接口方法必须使用Javadoc注释（@param、@return、@throws）**
- [ ] **方法参数必须有Javadoc注释（@param说明参数含义）**
- [ ] **方法返回值必须有Javadoc注释（@return说明返回值含义）**
- [ ] **枚举字段必须有注释说明其业务含义**
- [ ] 关键逻辑有注释说明"为什么这样做"（不是"做什么"）
- [ ] 方法长度适中，单个方法不超过一屏

**可维护性**

- [ ] 无硬编码魔法值，常量抽取到常量类或配置
- [ ] **DTO字段（如pageNum、pageSize）不应加默认值**
- [ ] **不要显式创建线程，请使用线程池**
- [ ] 重复代码已抽取为公共方法
- [ ] 外部依赖通过接口抽象，便于替换

**一致性**

- [ ] 遵循项目编码规范
- [ ] 日志级别使用正确（info/warn/error 区分）
- [ ] 异常处理策略与详细设计一致
- [ ] Shell 脚本中无中文标点符号（`，。：""（）` → `,.:""()`）

**安全性**

- [ ] 通过 `secure-coding.md` 的 16 项自检清单
- [ ] 敏感数据处理（加密、脱敏）按设计执行

**测试**

- [ ] 单元测试覆盖所有业务方法
- [ ] 测试用例名称清晰表达意图
- [ ] 无被忽略或注释掉的测试

### Step 11：工程卫生检查

**反编译文件检查**：扫描项目根目录及所有非 `src/` 目录下的 `.java` 文件：

```bash
find . -name "*.java" | grep -v "/src/" | grep -v "target/"
```

如有输出，说明存在反编译/参考副本，提醒用户确认后删除。理由：这类文件不参与 Maven 编译，但工程师看到后容易误以为是项目源码，增加认知负担。

**知识沉淀**：实现过程中查阅 JAR 包、解决依赖问题、发现框架约束时，将关键发现整理为文档：

- 路径：`docs/知识沉淀/{分类}-{主题}.md`（如 `maven-local-cache.md`、`spring-event-listener.md`；`知识沉淀/` 目录如不存在则创建；文件数超过 15 个时改用子目录 `docs/知识沉淀/{分类}/{主题}.md`）
- 文档格式：使用场景 → Maven 坐标（如适用）→ 代码示例 → 常见错误与正确写法

**应当沉淀的内容**：

- 通过 `jar tf` / `javap` 发现的框架类结构、版本间破坏性变更（如类重命名）
- 模块依赖约束（如某模块不能引入 Servlet 依赖的原因）
- 框架 API 非显而易见的用法规则（如 `setData` 的重载选择规则）
- Maven 本地缓存失效问题及刷新方法

### Step 12：CI/CD 集成建议

如果项目使用 CI/CD，建议在流水线中加入以下环节（具体工具由项目选择）：

| 阶段 | 检查项 | 失败处理 |
|------|--------|----------|
| 构建 | 编译通过 | 阻断 |
| 静态扫描 | **编码规范 + SonarQube扫描** | **阻断（包含Javadoc、枚举注释、DTO默认值、魔法值等检查）** |
| 静态扫描 | 安全扫描（Checkmarx等） | 高危问题阻断 |
| 单元测试 | 全部通过，覆盖率 ≥ 约定阈值 | 阻断 |
| 集成测试 | 核心接口冒烟测试 | 阻断 |
| 制品产出 | 打包并标记版本 | - |
| 部署 | 按环境差异化部署（Mock/真实实现切换等） | 人工确认 |

**实现阶段的 CI/CD 输出**：

- 在实现记录中记录"本次构建产物"（jar/image/二进制名称和版本号）
- 在实现记录中记录"CI/CD 配置文件位置"（如 `.gitlab-ci.yml`、`.github/workflows/`）

## 注意事项

- 编码规范检查是硬性前置条件，没有规范文件就不写代码
- 代码中不硬编码配置项，使用配置文件或配置中心
- 注意目标数据库的 SQL 兼容性（如分页语法、函数差异等）
- 每次用户触发本 skill 时都要重新检查编码规范文件
- 00-计划与执行.md 是活文档，编码过程中持续更新进度
- **Shell 脚本中禁止使用中文标点符号**（如 `，`、`。`、`：`、`""`、`（）`），必须使用英文标点。中文标点在 bash 中不被识别为语法符号，会导致命令解析失败且报错信息极难排查
- **跨 skill 引用**：执行本 skill 时可引用其他已存在的 skill（如安全扫描、代码评审）；用户对 skill 使用有明确偏好时优先满足，**但 Step 1 编码规范前置检查不被偏好覆盖，必须执行**（详见 `backend-dev/SKILL.md` 「跨 Skill 引用与协作原则」）
- **修订记录**：产出文档末尾加「修订记录」章节，格式 `| 版本 | 日期 | 变更人 | 变更说明 |`；新建记 `v0.1 | YYYY-MM-DD | 作者 | 初稿`，后续修改只追加行
