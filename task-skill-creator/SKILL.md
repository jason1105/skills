# Task Creator — 任务经验 Skill 化

将已完成任务的执行经验提炼为结构化的 skill，使相同或相似的任务下次能被更高质量地执行。

**task-skill-creator 的职责边界**：只负责创建和维护 skill，不负责执行任务。任务的执行、产出物的生成由任务本身或已有的 skill 完成。task-skill-creator 在任务完成之后介入。

## 核心原则

1. **后置介入**：task-skill-creator 在任务完成后才工作，基于上下文回顾来创建 skill，而非先创建 skill 再执行任务。
2. **绝不猜测**：任何不能 100% 确定的内容，都必须向用户确认后再执行。
3. **递归拆解**：复合任务的 skill 可以引用子任务 skill，形成层级结构。
4. **持续进化**：skill 随使用不断改进，通过学习日志记录每次变更。

---

## 触发时机

### 主动触发（推荐）

用户在任务完成后明确要求：

- "把刚才做的事情变成 skill"
- "为这个任务创建 skill"
- "记住这个做法，下次还要用"

### 自动提议

当以下条件同时满足时，主动向用户提议创建 skill：

1. 一个任务刚刚完成（对话中有明确的任务执行过程和结果）
2. 该任务具有可复用性（不是一次性的、特定场景的操作）
3. 当前不存在覆盖该任务的 skill

提议方式：

> 刚才的任务看起来有复用价值。需要我把它提炼成一个 skill，方便下次直接使用吗？

用户肯定回答后，进入执行流程。用户拒绝则不再追问。

---

## 与 update-skill 的分工

两个 skill 都涉及对 skill 的修改，但触发时机和适用场景完全不同：

| | **update-skill** | **task-skill-creator** |
|---|---|---|
| **触发时机** | 使用某 skill 执行任务的过程中，用户对结果不满意或给出反馈 | 任务完成后，主动提炼执行经验 |
| **触发方式** | 自动触发，无需用户显式调用 | 用户主动发起，或由 task-skill-creator 主动提议 |
| **操作范围** | 针对已有 skill 的局部修改（最小化更新） | 创建新 skill，或系统性地合并新经验 |
| **流程重量** | 轻量（3 步）：识别反馈 → 更新 → 确认 | 重量（5 步）：回顾 → 查重 → 层级 → 创建 → 日志 |

**判断原则**：

- 刚刚用某个 skill 做了任务，用户指出"这里不对"或"以后要这样" → **走 update-skill**
- 一个任务完成了，想把整个执行经验固化下来 → **走 task-skill-creator**

## 执行流程

### Step 1：回顾上下文，总结任务（⚠️ 需确认）

回顾当前对话中的任务执行过程，提取以下信息：

1. **任务目标**：这个任务要达成什么
2. **执行步骤**：实际做了哪些操作，按什么顺序
3. **使用的工具**：调用了哪些 skill、MCP、命令行工具等
4. **输入输出**：任务的输入是什么，产出了什么
5. **关键决策**：过程中做了哪些判断和选择，为什么
6. **踩过的坑**：遇到了什么问题，怎么解决的
7. **用户的修正**：用户纠正了哪些做法

将总结呈现给用户，**逐条确认**：
- 有没有遗漏的步骤？
- 有没有理解错的地方？
- 哪些是通用做法，哪些是本次特殊处理？

只有用户确认无误后，才进入下一步。

### Step 2：检查已有 skill（自动执行）

依次在当前项目目录和用户 skill 目录中搜索是否已存在匹配当前任务的 skill：

```bash
# 1. 搜索当前项目目录
find . -name "SKILL.md" 2>/dev/null
grep -rl "相关关键词" $(find . -name "SKILL.md") 2>/dev/null

# 2. 搜索用户 skill 目录
ls ~/.claude/skills/ 2>/dev/null
grep -r "相关关键词" ~/.claude/skills/*/SKILL.md 2>/dev/null
```

- **已存在** → 告知用户，进入"更新模式"（在现有 skill 基础上合并新经验）。
- **不存在** → 进入"新建模式"。

### Step 3：确定 skill 层级关系（⚠️ 需确认）

#### 3a. 查找父任务 skill

判断当前任务是否属于某个更大任务的子任务（一个任务可以有多个父任务）。

- **找到父任务 skill** → 询问用户是否将当前 skill 作为子任务关联到父 skill 中。
  - 用户同意 → 后续更新父 skill 的子任务列表。
  - 用户拒绝 → 跳过。
- **未找到** → 跳过。

#### 3b. 分析任务结构

判断当前任务是**原子任务**还是**复合任务**：

- **原子任务**：不可再拆分，skill 直接描述完整执行步骤。
- **复合任务**：包含多个可独立复用的子任务，skill 中列出子任务清单并引用各子任务 skill。

将分析结果告知用户并确认。

### Step 4：调用 skill-creator 创建 skill（⚠️ 需确认）

本步骤将 Step 1-3 收集的信息交给 **skill-creator** 来完成 SKILL.md 的编写、测试和迭代。skill-creator 是专门用于创建高质量 skill 的工具，包含编写规范、测试流程和质量保障机制。

#### 4a. 准备交接材料

将 Step 1-3 的成果整理为 skill-creator 所需的输入：

| skill-creator 需要的信息 | 来源 |
|--------------------------|------|
| 这个 skill 要做什么 | Step 1 的任务目标 |
| 什么时候触发 | Step 1 的任务场景 + Step 3 的层级关系 |
| 执行步骤和工具 | Step 1 的执行步骤、使用的工具 |
| 输入输出格式 | Step 1 的输入输出 |
| 边界情况和陷阱 | Step 1 的踩坑经验、用户修正 |
| 哪些是通用做法 | Step 1 确认中用户区分的通用 vs 特殊处理 |
| 是否有父/子 skill 关系 | Step 3 的层级分析结果 |
| 是新建还是更新 | Step 2 的查重结果 |

#### 4b. 调用 skill-creator

将交接材料作为上下文，按 skill-creator 的流程执行：

1. **编写 SKILL.md**：skill-creator 会根据其编写规范生成 SKILL.md，包括：
   - pushy 的 description（提高触发准确率）
   - 祈使句式的执行步骤
   - progressive disclosure 结构（SKILL.md < 500 行，大块内容放 references/）
   - 跨 skill 通用规范的继承（产出物规范、命名规范，见下方"跨 Skill 通用规范"）

2. **测试**：skill-creator 会生成 2-3 个测试用例，模拟执行并呈现结果给用户审查。
   - 在 Claude Code 中：可用 subagent 并行测试
   - 在 claude.ai 中：逐个模拟执行，将结果直接呈现在对话中

3. **迭代**：根据用户反馈修改 SKILL.md，重新测试，直到用户满意。

#### 4c. 复合任务的额外处理

如果 Step 3b 判定为复合任务：

- skill-creator 先创建父任务 skill，列出所有子任务及执行顺序
- 然后对每个子任务，询问用户是否也需要创建独立 skill：
  - 用户同意 → 对该子任务**从 Step 1 重新执行 task-skill-creator 全流程**（递归）
  - 用户拒绝 → 仅在父 skill 中内联描述该子任务

#### 4d. 更新模式的额外处理

如果 Step 2 判定为更新模式：

- 读取已有 SKILL.md，将本次执行经验作为增量输入传给 skill-creator
- skill-creator 对比新旧内容，合并新发现的步骤或注意事项
- 如有矛盾，向用户确认以哪个为准
- 保留原有的 name 和目录名不变

**所有创建和修改操作完成前，将 SKILL.md 全文呈现给用户做最终确认。**

### Step 5：记录学习日志（自动执行）

将本次创建或更新记录写入 `CHANGELOG.md`。

## 自学习系统

skill 体系通过"使用 → 反馈 → 沉淀 → 进化"形成闭环。

### 学习日志

每个 skill 目录下维护 `CHANGELOG.md`：

```markdown
# [Skill 名称] 学习日志

## [YYYY-MM-DD] v1.1 — [简述改进]
- **来源**：执行任务 "[任务名]" 时发现
- **问题**：[原来的做法有什么不足]
- **改进**：[更新了什么内容]
- **影响范围**：[修改了 SKILL.md 的哪个部分]

## [YYYY-MM-DD] v1.0 — 初始创建
- 由 task-skill-creator 从任务执行经验中提炼生成
```

### 自学习触发条件

以下情况发生时，应使用 task-skill-creator 更新相应 skill：

| 触发场景 | 说明 |
|----------|------|
| **用户纠正** | 用户指出 skill 中的做法有误并给出正确方式 |
| **重复修改** | 同一类问题在不同任务中被修正 2 次以上 |
| **流程缺口** | 执行中发现 skill 未覆盖的必要步骤 |
| **更优方案** | 发现比 skill 中记录的更高效的做法 |
| **边界场景** | 遇到 skill 未预见的特殊情况 |
| **领域知识** | 任务执行中学到的专业知识 |

### 自学习执行规则

1. **永远先问再改**：所有更新必须经用户确认。
2. **最小化修改**：只更新与经验直接相关的部分。
3. **保留历史**：每次更新记录到 `CHANGELOG.md`。
4. **向上传播**：仅在新创建子 skill 时，提议将其关联到父 skill。子 skill 的后续更新不再自动向上传播。
5. **向下传播**：父 skill 改进若影响子 skill，提议同步更新。
6. **跨任务传播**：通用性经验提议更新 task-skill-creator 自身。

### Skill 体系审视（用户触发）

当用户要求"审视 skill 体系"、"检查一下现有的 skill"时执行。

**第一步：扫描现有 skill**

```bash
for dir in . ~/.claude/skills; do
  find "$dir" -name "SKILL.md" -exec echo "=== {} ===" \; -exec head -10 {} \; 2>/dev/null
  find "$dir" -name "CHANGELOG.md" -exec echo "--- {} ---" \; -exec cat {} \; 2>/dev/null
done
```

**第二步：生成审视报告**，呈现给用户确认后再执行任何修改：

| 审视维度 | 检查内容 |
|----------|----------|
| **冗余** | 多个 skill 覆盖高度重叠的功能 → 提议合并 |
| **缺口** | 已有 skill 之间缺少应有的 skill → 提议新建 |
| **一致性** | 父子 skill 之间存在矛盾或过时引用 → 提议修正 |
| **质量** | CHANGELOG 中频繁出现修正记录的 skill → 提议重构 |
| **公共模式** | 多个 skill 中反复出现相同步骤或约束 → 提议抽取为公共 skill |

## Skill 目录结构

```
<skill-name>/               # skill 标识，英文小写+中划线
├── SKILL.md                # 执行指南（怎么做）
├── CHANGELOG.md            # 学习日志（怎么演进的）
└── references/             # 可选：参考资料（做的时候要查的东西）
    └── *.md
```

skill 目录只存"知识"，不存任务产出物。产出物的存放规则由各 skill 自行定义。

## 跨 Skill 通用规范

以下规范适用于 task-skill-creator 生成的所有 skill，每个 skill 的 SKILL.md 中应包含或继承这些规则：

### 产出物规范

- 所有 skill 产出的文档使用 **Markdown 格式**
- 产出物存放在项目的 `docs/` 目录下，按模块组织子目录
- 产出物的文件和文件夹必须使用**补零编号 + 中划线**命名

| 对象 | 规则 | 示例 |
|------|------|------|
| `docs/` 下的文件夹 | `NN-中划线名称` | `00-整体计划`、`01-用户认证` |
| `docs/` 下的文档 | `NN-中划线名称.md` | `00-任务计划.md`、`01-接口设计.md` |
| 编号起始 | 从 `00` 开始 | `00` 保留给计划/概览文档 |

### 命名规范

| 对象 | 规则 | 示例 |
|------|------|------|
| skill 目录名 | 英文小写 + 中划线 | `user-auth`、`data-pipeline` |
| SKILL.md 中的 name | 与目录名一致 | `user-auth` |

## 已知陷阱

1. **跳步倾向**：执行时容易从 Step 1 直接跳到 Step 4（创建 skill），跳过 Step 2（查重）和 Step 3（层级关系）。原因是 Step 1 总结完任务后，心理上觉得已经"理解了"，急于开始创建。**对策**：每完成一个 Step，先说出下一个 Step 的编号和名称再开始执行。
2. **确认缺失**：标注了 ⚠️ 的步骤容易在自己分析完后就直接继续，忘记把结果呈现给用户确认。尤其是 Step 3（层级关系），分析结果看起来"显而易见"时最容易跳过确认。**对策**：每个 ⚠️ 步骤必须以向用户提问结尾，且在收到用户回复之前不得进入下一步。

---

## 关键约束

- **职责单一**：task-skill-creator 只创建和维护 skill，不执行任务，不产出任务交付物。
- **后置介入**：必须在任务完成后才工作，基于实际执行经验创建 skill，而非凭空设计。
- **确认优先**：所有标注 ⚠️ 的步骤必须等待用户确认。
- **不可跳步**：严格按 Step 1 → 2 → 3 → 4 → 5 执行。
- **递归一致**：子任务 skill 的创建遵循完全相同的流程。
- **幂等安全**：skill 已存在时进入更新模式，不重复创建。
- **改前必问**：任何 skill 的创建和修改，最终版本必须经用户确认。
- **可追溯性**：所有变更记录在 CHANGELOG.md 中。
